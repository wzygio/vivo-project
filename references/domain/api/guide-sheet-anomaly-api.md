# 异常片／Lot API 服务部署说明

更新日期：2026-11-11。面向安装、启动和维护服务的人员。

本文维护 API 概念、部署配置、启动操作与数据准备步骤。请求参数、返回字段和跨设备测试统一见 [API 调用说明](api-caller-guide-2026-11-03.md)；程序组成与处理流程见 [API 程序介绍](architecture-sheet-anomaly-api.md)。

## 1. API 与部署方式

API 是供程序读取数据的入口。人打开报表看表格，程序调用 API 则收到 JSON 数据，再用于自己的系统或表格。本服务提供异常片／Lot 明细及 SPC CPK／CPM 周度不达项，只读本地结果，不因请求而查询生产数据库或重新分析。

| 概念 | 在本项目中的含义 |
|---|---|
| 服务端 | 运行 API 的 Windows 电脑，读取本地配置和已发布结果 |
| 调用方／客户端 | 通过网络取数的其它电脑或系统 |
| URL、端口 | URL 是访问地址；端口区分同一电脑上的不同服务，API 当前使用 8890 |
| GET、查询参数 | GET 表示读取；参数用于选择产品、分类、日期等范围 |
| 请求头、API Key | 随请求提交的身份凭证；本接口使用 `X-API-Key` |
| JSON、HTTP 状态码 | JSON 是返回数据格式；状态码说明请求成功或失败 |
| HTTPS 网关 | 在 API 前提供统一入口和加密转发的服务；本机内网直连也可以使用 API |

当前已批准方案为 Windows 本机内网 HTTP 直连：`http://10.72.26.31:8890`。HTTP 不加密密钥；如改用 HTTPS，由运维提供证书和入口。IP 变化后需通知调用方，监听 `0.0.0.0` 本身不是可填写到客户端的访问地址。

API 与 Streamlit 报表独立运行。关闭报表页面不等于关闭 API；启动 API 也不会自动更新各来源的报表结果。

## 2. 部署前准备

1. 在部署电脑保留项目、配置、维护工作簿和已发布结果，使用项目 `.venv`，按既有依赖管理方式准备环境。依赖包括 FastAPI、Uvicorn、psutil；企业保护文件的读取还需现有 Excel／Office 环境及权限。
2. 用将来运行服务的 Windows 用户操作。授权摘要和登录启动项都属于该用户，换账号后不能直接沿用另一用户的配置。
3. 确认 8890 未被其它程序占用、调用设备能访问该内网。网络或防火墙问题由维护者按企业规则处理。
4. 按第 4 节配置调用方凭证，按第 5 节准备业务来源。服务就绪和来源就绪需要分别确认。

本文的 Python 命令统一使用 `uv run --no-sync python`，请先安装 uv，并在项目根目录执行。它使用已准备好的项目环境，`--no-sync` 避免日常运行时自动同步依赖；首次安装或依赖更新仍按项目流程单独完成。一键启动脚本内部继续直接定位项目解释器，无需依赖 uv 命令。

## 3. 一键启动与日常管理

### 3.1 已完成首次配置：双击启动

在项目根目录双击 [start_anomaly_api.cmd](../../../../start_anomaly_api.cmd)。它会调用 [PowerShell 启动脚本](../../../../tools/start_anomaly_api.ps1)，自动定位项目虚拟环境，并复用 [后台托管工具](../../../../tools/anomaly_api_service.py)。不需要先激活环境，也不需要管理员权限。

启动脚本执行以下操作：

1. 检查虚拟环境、托管工具和当前用户的部署配置是否存在。
2. 请求托管工具启动 API；若已经运行，复用已有实例。
3. 检查监督进程、监听归属及 `/health/ready`，全部正常才提示 `API is ready`。

成功后 API 在后台运行，关闭启动窗口不会停止服务。脚本不会重写密钥、不安装依赖、不修改监听配置、不自动停止或重启已有服务。端口被其它程序占用、缺少配置或已有进程未就绪时，会报错并保留现有状态，按第 7 节排查。

也可在项目根目录的 PowerShell 中执行，便于看到退出状态：

```powershell
.\tools\start_anomaly_api.ps1
```

脚本退出码：`0` 表示本次已核实服务就绪，`2` 表示启动或核实失败。CMD 窗口会保留提示，按任意键后关闭。若企业策略阻止运行 PowerShell 脚本，请由 IT 按策略处理；不要为了启动服务全局放宽脚本执行策略。

### 3.2 首次部署：设置凭证

如果提示缺少 `deployment.json`，先在项目根目录运行：

```powershell
powershell.exe -NoProfile -STA -File tools/setup_anomaly_api_credentials.ps1
```

窗口要求输入并确认自行保管的随机密钥，范围为 32～256 个无空格 ASCII 字符。请先在密码管理器中生成并保存。现有设置窗口使用已批准的 7 个产品、ARRAY／OLED／TP 和全部 6 类来源；新部署范围不同，应先由维护者调整授权方案。

窗口只保存摘要，不保存原始密钥；保存后会启动 API、验证带密钥的 OpenAPI，并安装当前用户登录启动项。已有部署配置时窗口拒绝覆盖，不要删除配置来重新设置。首次启动失败后摘要可能已经保存，此时核对日志后用一键脚本恢复，不要重复生成调用方密钥。

### 3.3 查看、停止与更新

从项目根目录查看状态：

```powershell
uv run --no-sync python tools/anomaly_api_service.py status
```

重点看 `supervisor_alive`、`listener_owned`、`ready` 是否均为 `true`；`status=running` 单独不能证明服务正常。`ready=true` 只检查服务配置，不保证每个业务来源可用。

#### 为什么任务管理器中有多个 Python 进程

后台托管工具包含两个职责，不能仅凭相同脚本名判断重复启动：

| 命令行中的动作 | 职责 |
|---|---|
| `anomaly_api_service.py run` | 监督进程，启动工作进程，并在工作进程异常退出后按退避策略重启 |
| `anomaly_api_service.py worker` | API 工作进程，运行 Uvicorn 并处理 HTTP 请求；代码明确配置 `workers=1` |

当前 Windows 部署使用项目虚拟环境的 `pythonw.exe`。虚拟环境启动器会调用基础 Python 解释器，因此每个职责还会显示一对父子进程，正常运行时可看到以下四层关系：

```text
.venv\Scripts\pythonw.exe  … anomaly_api_service.py run     （启动器）
└─基础 Python\pythonw.exe  … anomaly_api_service.py run     （监督进程）
  └─.venv\Scripts\pythonw.exe  … anomaly_api_service.py worker  （启动器）
    └─基础 Python\pythonw.exe  … anomaly_api_service.py worker  （API 服务）
```

这里的“基础 Python”指创建虚拟环境时使用的解释器目录，可在 `.venv/pyvenv.cfg` 的 `home` 字段核对。因此，两条 `run` 和两条 `worker` 可以属于同一套 API；它们不是四个独立 API 实例，也不是 Uvicorn 多 worker 部署。

判断是否重复启动，应结合父子关系、监听归属和前述 `status` 结果。在任务管理器的“详细信息”页启用“命令行”列可区分 `run` 与 `worker`；需要核对父子关系时，在项目根目录的 PowerShell 执行：

```powershell
Get-CimInstance Win32_Process |
    Where-Object { $_.Name -eq 'pythonw.exe' -and $_.CommandLine -like '*anomaly_api_service.py*' } |
    Select-Object ProcessId, ParentProcessId, ExecutablePath

Get-NetTCPConnection -State Listen -LocalPort 8890 |
    Select-Object LocalAddress, LocalPort, OwningProcess
```

将 `ParentProcessId` 与上一层的 `ProcessId` 对应，再将 `OwningProcess` 与实际 API 工作进程对应。端口使用部署配置中的值；当前为 `8890`。本次核查（2026-11-11）中，四个进程构成一条父子链，只有最末层工作进程监听 `0.0.0.0:8890`，且 `supervisor_alive`、`listener_owned`、`ready` 均为 `true`，`restarts=0`，确认没有重复启动。PID 在重启后会变化，不应固定使用本次 PID 识别服务；`restarts` 表示工作进程重启次数，不表示实例数量。

日常重复点击一键启动时，托管工具发现已有监督进程会返回 `already_running`，并使用 `host.lock` 防止同一运行目录出现多个监督循环。若发现另一条独立进程链或监听归属不符，应进一步核对启动方式和运行目录；不要直接按进程名批量结束 Python。

#### 停止、更新与登录启动

维护时如需停止，由维护者执行：

```powershell
uv run --no-sync python tools/anomaly_api_service.py stop
```

更新程序或调用方授权后，由维护者安排停机，再执行停止命令和一键启动脚本。托管工具核实 PID 与创建时间后只处理自己记录的 API 进程，不停止 Streamlit。重启会使旧分页游标失效。

首次设置会创建当前用户启动目录下的 `Tianzhu Anomaly API.lnk`。已有配置但尚未安装登录启动项时，可在确认没有同名启动项且服务已停止后执行：

```powershell
uv run --no-sync python tools/anomaly_api_service.py start --install-startup
```

该选项用于新启动流程，服务已运行时不会补装，需由维护者安排停止后再执行。已有同名项时先核实，不要重复安装。

这是**登录后自动启动**，不是 Windows 系统服务。电脑需开机、唤醒并保持该用户登录；注销、休眠或关机时不保证可调用。只停止进程不会删除启动项；永久取消时，由用户删除上述专用快捷方式。无人值守运行需运维另行设计账号和托管方式。

### 3.4 部署检查

| 检查 | 地址／方式 | 说明 |
|---|---|---|
| 本机存活 | `http://127.0.0.1:8890/health/live` | 预期 `{"status":"ok"}`，不访问数据库 |
| 本机就绪 | `http://127.0.0.1:8890/health/ready` | 检查凭证和启用产品配置 |
| 其它设备访问 | `http://10.72.26.31:8890/health/live` | 必须在另一台设备验证，不能用本机结果代替 |
| 业务取数 | 按 [调用说明](api-caller-guide-2026-11-03.md) 执行 | 带密钥，并核对来源完整性与一条真实记录 |

健康接口不需要密钥。业务接口及 `/openapi.json` 需要密钥；当前没有 `/docs`、`/redoc` 交互页面。

### 3.5 在本机完成一次取数测试

以下操作在**部署 API 的这台电脑**上完成，用已有查询窗口测试正式服务。无需另开 Uvicorn 或停止现有服务；如果服务尚未启动，先双击项目根目录的 `start_anomaly_api.cmd`。

**第一步：确认服务能响应。** 在本机浏览器打开 `http://127.0.0.1:8890/health/live`，应显示 `{"status":"ok"}`。这一步不需要密钥，只证明服务存活，后面还要实际取数。

**第二步：打开查询窗口。** 在项目根目录的 PowerShell 中执行：

```powershell
uv run --no-sync python tools/fetch_sheet_anomalies.py
```

不传参数即打开可视化窗口。若已设置 `API_KEY`／`VIVO_API_KEY` 进程环境变量，密钥框会用星号自动填入；否则在窗口输入现有原始密钥。此命令不会自动读取项目 `.env`，配置规则见第 4.3 节。

**第三步：填写一组可重复核对的条件。**

| 窗口字段 | 填写内容 |
|---|---|
| API 地址 | `http://127.0.0.1:8890`，不要追加接口路径 |
| API Key | 保留环境变量自动填入的内容，或手动输入原始密钥 |
| 产品 | `M626` |
| 分类 | `SPC` |
| 异常事件 | `全部` |
| 开始日期 | `2026-10-26` |
| 截止日期 | `2026-11-01` |
| 每页行数 | 留空 |

点击 **“查询完整结果”**。以上日期固定为 2026-W44，便于重复核对；日常查询上周时，将两个日期框都清空即可。事件选“全部”时，程序省略 `event_type`，服务会查询 SPC 支持的四种事件。

2026-11-04 的正式实测结果为 **2 项：CPK、CPM 各 1 项，各包含 3 个 Sheet ID**，`meta.complete=true`；OOS、OOC 当时均为 0 项。数据维护或规则调整后结果可能变化，不能只凭固定条数判断服务是否正常。

**第四步：判断结果是否完整。** 窗口中会显示状态、查询时段和 JSON 预览：

| 看到的结果 | 如何判断 |
|---|---|
| `meta.complete=true`，且有明细 | 查询成功，选中来源均可用 |
| `meta.complete=true`，明细为空 | 查询成功，当前条件下没有可返回的异常 |
| `meta.complete=false` | 取得可用部分；查看 `failed_sources`，不能作为完整统计 |
| 401／密钥无效 | 核对原始密钥是否与服务配置对应；自动填入不等于免认证 |
| `result_unavailable`／503 | 所选来源暂不可用，按第 5、7 节检查来源资料 |
| `read_timeout`／503 | API 已响应，但汇总读取超过 90 秒；缩小产品／分类后重试，维护者按请求编号查 `API_READ_TIMEOUT` 日志 |
| 连接失败 | 核对地址、端口及第 3.3 节的服务状态 |

这里的“2 项”是能力项目数，不是去重片数；能力记录的“对象编号”是片号列表。预览最多显示 20 行，不代表查询或下载只取 20 行。

**第五步：检查分页和下载。** 保持同一组条件，把“每页行数”改成 `1` 再查询。程序会自动取完全部页，结果应与不分页一致；上述实测案例为 2 页，可在 `client.pages_fetched` 查看页数。点击 **“下载全部明细(CSV)”** 或 **“保存完整响应(JSON)”**，在保存对话框选择位置。CSV 的片号列表保存为标准 JSON 文本，另附 `.csv.meta.json` 完整性说明；部分成功时按钮显示“下载可用部分(CSV)”，文件名会带 `-partial`。

需要测试默认全选时，再清空产品、将分类和事件都选“全部”，日期留空后查询。这会查询全部授权范围的上周数据，可能出现更多缺资料的来源组合；只要窗口明确显示 `complete=false` 和失败来源，就表示返回的是可用部分，不能将缺资料解释为没有异常。

完成后关闭查询窗口即可，后台正式 API 会继续运行。本机测试不能替代其它设备的网络访问测试；在其它 Python 程序中调用的方法见 [调用说明](api-caller-guide-2026-11-03.md)。

## 4. 调用方凭证与授权配置

### 4.1 当前用户的部署配置

托管配置位于 `%LOCALAPPDATA%\Tianzhu\AnomalyApi\deployment.json`，包含版本、项目绝对路径、监听地址、端口及调用方清单。当前方案监听 `0.0.0.0:8890`；`127.0.0.1` 仅供本机。托管工具只接受这两种监听地址。项目迁移后维护者需核对 `project_root`，不能照搬旧绝对路径。

配置包含摘要和授权，不包含原始密钥，不加入 Git。每个调用系统使用独立密钥；原始密钥由维护者通过企业批准的凭据渠道交付。调用方、摘要不得重复，产品／厂别／分类列表不能为空。

### 4.2 工作进程的凭证格式

托管工具将配置中的 `clients` 注入 API 工作进程的 `VIVO_API_CLIENTS` 环境变量。直接运行 Uvicorn 时，需要在同一进程环境中准备该变量。其格式如下，全部占位内容必须替换：

```json
[
  {
    "client_id": "report-demo",
    "key_sha256": "<原始密钥的64位小写SHA-256摘要>",
    "products": ["PRODUCT_DEMO"],
    "factories": ["ARRAY"],
    "sub_domains": ["SPC", "CTQ", "AOI_TT", "AOI_RS", "Yield", "Q-Time"]
  }
]
```

产品实际可查询范围是调用方授权与项目启用产品的交集。模板见 [api-clients.example.json](../../../../config/api-clients.example.json)，全零摘要和虚构产品不能直接使用。首次配置优先使用前面的设置窗口；新增调用方由维护者生成独立摘要并按需授权。

API 每次鉴权读取本进程环境。编辑外部终端环境或磁盘部署配置不会自动更新已运行的工作进程，需要维护者安排重启。不要把原始密钥写入 Git、业务 YAML、URL、日志或浏览器前端源码。

### 4.3 API Key 是否必须，能否默认填入

API Key 不是 HTTP／API 技术上的必选项，而是当前服务采用的认证方式。服务用它识别调用方，再应用对应产品、厂别、分类授权和限流。直接取消现有校验会失去这些按调用方划分的控制，需要另行确定匿名开放范围或替代认证方式。当前保留原认证及密钥，不开放匿名查询。认证工具的可选机制可参考 [FastAPI 官方说明](https://fastapi.tiangolo.com/reference/security/#fastapi.security.APIKeyHeader)。

需要免去反复输入时，可在调用程序的运行环境中配置 `API_KEY`（例如 IDE 的运行配置）；配套窗口和命令行会自动读取，兼容 `VIVO_API_KEY`，窗口以星号显示。客户端每次自动附上请求头，服务端仍检查它。不设置通用默认密钥，不把密钥写入共享代码或文档，也不为无密钥请求代填。

当前直接使用 `uv run --no-sync python tools/fetch_sheet_anomalies.py` 打开窗口，程序不会自动读取项目 `.env`；已有进程环境变量可自动填入，否则手动输入。其它系统按自己的配置方式读取并传入密钥，不分发本机密钥。原查询 CMD 和独立启动器已按用户要求移除，API 服务启动入口仍见第 3.1 节。

### 4.4 手动前台运行（维护用途）

这条命令的作用是：**在当前终端直接启动一个 API 服务，供维护者在本机检查启动过程、查看错误或临时排查问题。它是启动服务的命令，不是查询异常数据的命令。** 日常使用按第 3 节双击一键启动即可，无需再执行本节命令。

“前台运行”表示服务占用当前 PowerShell 窗口：执行后会持续等待请求并显示运行日志，不会立即回到命令输入提示符。需要保持窗口打开；按 Ctrl+C 会停止本次服务，关闭窗口也会结束此次前台运行。

确认 8890 未被正式实例或其它程序占用，并在当前终端准备好第 4.2 节的 `VIVO_API_CLIENTS` 后，从项目根目录执行：

```powershell
uv run --no-sync python -m uvicorn api.main:create_app --factory --host 127.0.0.1 --port 8890 --workers 1 --no-access-log
```

你看到的旧写法 `.venv/Scripts/python.exe -m uvicorn ...` 也是同样的启动方式，只是直接指定项目 Python 的路径；本文现已统一使用上面的 uv 写法。

| 命令部分 | 含义 |
|---|---|
| `uv run --no-sync python` | 使用已经准备好的项目 Python 环境，不在本次启动时同步依赖 |
| `-m uvicorn` | 运行 Uvicorn。它负责监听网络请求，并将请求交给 API 程序处理；uv 与 Uvicorn 是两个不同工具 |
| `api.main:create_app` | 在 `api/main.py` 中找到创建 API 应用的 `create_app` 函数 |
| `--factory` | 调用这个函数，得到本次要运行的 API 应用 |
| `--host 127.0.0.1` | 只接受这台电脑上的访问，其它电脑无法通过此监听地址调用 |
| `--port 8890` | 使用 8890 端口；同一监听地址的该端口不能再被其它实例占用 |
| `--workers 1` | 使用一个工作进程；本项目的缓存和分页状态保存在进程内，当前按单进程部署 |
| `--no-access-log` | 关闭逐条 HTTP 访问日志，避免将查询 URL 写入默认访问日志；启动提示和错误日志仍会显示 |

例如启动成功后，可以在**本机另开浏览器**访问 `http://127.0.0.1:8890/health/live`，确认返回 `{"status":"ok"}`。健康检查通过只表示服务能响应，业务查询仍需凭证和可用的来源结果。

| 对比项 | 手动前台运行 | 第 3 节的一键后台启动 |
|---|---|---|
| 主要用途 | 本机临时检查和故障排查 | 日常运行服务 |
| 终端窗口 | 需要保持打开，日志直接显示 | 启动成功后可关闭窗口，服务继续运行 |
| 凭证加载 | 维护者在当前终端准备 `VIVO_API_CLIENTS`；不会自动读取托管配置中的凭证 | 托管工具读取当前用户部署配置并注入工作进程 |
| 异常退出恢复 | 此命令不提供后台监督重启 | 监督进程存活时，可对工作进程异常退出执行退避重启 |
| 登录启动项 | 此命令不创建 | 首次设置流程可创建；一键脚本本身不补装 |
| 访问范围 | 此示例仅限本机 | 以部署配置为准，当前方案供内网设备访问 |

排查结束后按 Ctrl+C 停止本次前台服务，再由维护者按需要恢复后台运行。不要在正式实例运行时直接执行本命令，也不要为了排查随意停止现有正式服务。需要归档的标准输出／错误按项目规则保存到 `output/logs/`，不记录密钥或完整请求头。Uvicorn 参数定义见 [官方设置说明](https://www.uvicorn.org/settings/)。

## 5. 业务来源与元数据准备

服务启动不代表来源就绪。请确认启用产品、公开政策、发布有效性、必要字段和人工释放决定都满足要求。公开政策缺失或无法读取时，接口不会输出该来源的数据。

资源路径由 [全局配置](../../../../config/global.yaml) 的 `resources` 统一解析，维护工作簿需要保留。客户端不能提交文件路径或工作表名。

### 5.1 初始化本地元数据

```powershell
uv run --no-sync python tools/sync_api_alert_metadata.py --initialize
```

这个命令会连接数据库，**读取完整工序字典并生成本地站点、描述、层别映射**，不再只是创建空模板。文件不存在时创建；已有文件时刷新匹配站点，保留其它工作表及本次源字典未包含的历史站点，并在替换前备份。配置键为 `resources.shared_kernel.files.api_alert_metadata`，默认位置为 `resources/shared_kernel/shared/api_alert_metadata.xlsx`，这是需要保留的维护资料。

读取优先使用 `mdw.dwr_mes_processoperationspec_v`，SQL 失败时才回退 `mdw.dwr_mes_processoperationspec`；读取 `oper_code` 和 `description` 均非 NULL 的记录。层别取描述第一个 `_` 之前的文字，并去掉两端空白：`PI2_CURE_THK` 对应 `PI2`。没有 `_` 时使用完整描述。

全量读取前先执行普通 `EXPLAIN (FORMAT JSON, VERBOSE)` 探查计划，再从 `pg_class`／`pg_namespace` 统计信息确认底层关系规模，不执行 `EXPLAIN ANALYZE` 或无界 `COUNT(*)`。默认最多接收 10,000 条源记录，并多取一条检测超限；查询在只读事务中执行，默认超时 10 秒。底层关系估计合计超过 10 万行、64 MiB，统计未知，或计划成本超过上限时拒绝读取。超限、数据库失败或同站点描述冲突时，不发布部分字典，也不覆盖原文件。完全相同的重复记录合并。

2026-11-03 已实际完成全量初始化：源记录 6,709 条，合并重复后共 6,700 个站点。返回如下，省略中文 `message`：

```json
{
  "status": "success",
  "created": false,
  "stations_updated": 6700,
  "initialized": true,
  "stations_total": 6700,
  "dictionary_state": "populated",
  "layers_complete": false,
  "stations_without_layer": ["1A455"]
}
```

`created=false` 只表示本次没有新建文件，不是失败；`stations_updated` 是本次从源字典同步的不同站点数，`stations_total` 包含保留的历史站点。以后需要完整刷新时，可以再次运行相同命令。

源站点 `1A455` 的描述是 `_DI_CDOL`，按规则得到空层别。程序保留真实记录、留空 `layer`，通过 `layers_complete=false` 和 `stations_without_layer` 提醒维护，不编造层别。其它站点可正常使用；API 若命中这条缺层别的记录，相关来源仍按字段完整性规则返回不可用。应维护权威工序描述后再同步。

站点字典保存以下列；Yield 不使用这份字典：

| 工作表 | 列名 | 维护内容 |
|---|---|---|
| `站点字典` | `step_id`、`description`、`layer` | 站点编号、原工序描述及自动生成的层别；编号以文本保存 |

HTTP 请求仍只读本地文件，不连接数据库。`layer` 为派生列，API 读取时也按 `description` 的相同规则取得层别，避免手工修改派生列造成口径不一致。

仅在离线测试或明确只需空模板时使用 `--template-only`；该选项不连接数据库，不等于完成全量初始化。`--initialize`、`--template-only` 和 `--step` 三种模式不能混用。

### 5.2 同步指定站点描述

已完成全量初始化后，只想更新个别站点时，可以执行下面的定向同步命令，无需每次重新读取完整字典。它和 5.1 都会访问数据库，但都独立于 API 请求：

```powershell
uv run --no-sync python tools/sync_api_alert_metadata.py --step "00100" --step "00200" --timeout-ms 10000 --max-rows 10000
```

先查询 `mdw.dwr_mes_processoperationspec_v`，SQL 执行失败才回退 `mdw.dwr_mes_processoperationspec`，按 `oper_code` 与 `description` 形成映射。查询使用明确站点集合、参数绑定、返回条数上限和事务内超时；每次最多指定 1,000 个站点，返回上限最多 10,000 行，超时范围 1～60,000 毫秒。

未查齐全部请求站点、同站点存在冲突描述或超过行数上限时，同步失败，不把部分结果当成完整字典发布。成功时更新请求站点及其派生层别，保留其它站点和已有工作表；重新从描述生成 `layer` 列。不要手填假描述来绕过缺层别问题。

Q-Time 的“发生站点”和层别均采用**起点 `f_step`**，所以必须维护起点的字典记录。

### 5.3 Yield 自动厂别与空层别

Yield Lot超规在原有计算与发布流程中保存`defect_group`和`factory`，API直接读取发布的`factory`，不再维护或查询`Yield归属`。映射在 [global.yaml](../../../../config/global.yaml) 中配置：

```yaml
data_source:
  defect_group_factory_mapping:
    Array_Line: ARRAY
    Array_Pixel: ARRAY
    Array_Mura: ARRAY
    OLED_Mura: OLED
    "TP_Short NG": TP
    "TP 容值NG": TP
```

配置不能为空，分组和厂别均为非空文本；厂别规范为大写。发布者在计算时读取当前配置，纯计算不读YAML。映射属于现有Yield策略签名的一部分，新增或修改映射后旧Yield发布可能变为stale，需按正常报表／发布流程重新生成；编辑映射本身不会改写结果，也不会延长数据有效期。

入库不良无法直接定位发生工序，因此Yield的`发生站点`和`层别`一律返回JSON `null`，不填写默认层别，不查询站点字典。厂别仍必须完整且满足调用方授权；未知分组的超规记录会保留在发布结果中，但厂别为空，明确释放后，该来源不可用；单独查询时返回503，跨来源查询时按部分失败规则处理。旧发布文件缺厂别时同样需正常重发，GET不会回退到人工归属或自行补算。其它来源仍要求真实站点及有效层别。

`Yield归属`已停用。2026-11-03按用户要求，已从`api_alert_metadata.xlsx`删除该历史工作表，站点字典保持不变，并保留删除前备份。初始化／同步命令不再要求或创建该表；其它历史文件不作批量清理。

### 5.4 维护人工释放决定

Inline OOS／OOC 沿用各自现有维护工作簿的 Flag。Q-Time 沿用原有人工决策台账；新的发布结果保留明确的 False 证据。旧 Q-Time 结果没有该证据时，需要正常 Q-Time 报表生产重新发布，API 不会在读取时补 False。

Yield 的持久决定位于 Lot 结果工作簿的 `<产品>__flags` 工作表。对已有、尚未初始化控制的产品显式执行：

```powershell
uv run --no-sync python tools/initialize_yield_alert_controls.py --product PRODUCT_DEMO
```

`PRODUCT_DEMO` 是虚构示例，执行时替换为已启用且已有发布结果的产品。命令不查询数据库、不运行 Yield 分析，也不刷新原发布时间；不存在发布结果时不能凭空初始化成功。

`<产品>__flags` 包含“超规 Lot ID”“异常 Code”“入库时间”“flag”。稳定键是前面三列，日期规范为 `YYYY/MM/DD`；产品由工作表归属确定。新异常默认 `True`，只有操作人员确认需要释放的键才改为 `False`。建议仅填写明确的 `True`／`False`，缺失、Delete 或不可识别值不会释放。

维护权威决定表，而不是只修改生成结果表中的同名列。正常发布会在文件锁内合并决定，保留人工历史和其他产品；本期不再出现的旧决定不会因此被删除。保存决定后读取会应用有效决定；若原发布已过期或失败，仍需原报表正常更新，编辑 Flag 不会延长数据有效期。

## 6. 日志、文件与运行限制

| 位置 | 用途 |
|---|---|
| `output/logs/anomaly-api/server.log` | 服务日志，按天轮转并保留 14 份历史文件 |
| `output/logs/anomaly-api/service.json`、`launch-*.json` | 进程身份、启动意图和运行状态，由托管工具维护 |
| `output/logs/anomaly-api/host-*.log` | 监督进程的启动与故障输出 |
| `resources/...` 中的发布结果、字典和决定表 | 按各来源生命周期保留，不能当缓存清理 |
| 进程内缓存和分页快照 | 可重建，重启后失效，不是业务历史资料 |

维护或同步工作簿应保留备份。Inline 当前没有统一“当日发布＋TTL”协议；Q-Time、Yield 检查各自已有的发布和健康规则，缓存有效期不会延长源数据有效期。

企业保护文件可能使用现有 Office COM 读取回退，必须验证正式账号的文件访问和 Office 环境。HTTP 超时不会强制终止卡住的 Office 调用，后台读取仍会占用有限槽位。并发、容量和限流的具体默认值见 [程序介绍](architecture-sheet-anomaly-api.md)。

默认全选最多串行检查 84 个产品／分类／事件组合。2026-11-11 排查确认原 30 秒总读取上限可使有效部分结果一并丢失，现调整为服务端 90 秒、查询程序每次 HTTP 请求默认等待 120 秒。超时仍返回 503，错误码为 `read_timeout`，服务日志记录请求编号、组合数与超时上限；不会无限等待或自动无限重试。Inline 异常台账只在产生异常时创建产品工作表；可读工作簿缺少产品工作表、有效空表和能力台账在所选周内无记录均返回成功空结果。文件缺失或读取错误仍需核对发布资料。

## 7. 常见故障处理

| 现象 | 处理顺序 |
|---|---|
| 一键启动提示缺文件 | 核对项目位置和 `.venv`；不要随意改用系统 Python |
| 缺少部署配置 | 用部署用户执行首次设置；已有配置不要删除 |
| 端口占用／启动失败 | 看启动窗口与日志，确认端口归属；不要直接结束未知进程 |
| `status=running` 但就绪字段为 false | 核对进程、监听与日志，维护者决定恢复方式；一键脚本不自动重启已有实例 |
| 本机可用、其它设备不可用 | 核对内网 IP、路由、企业代理和访问规则 |
| 401／403 | 核对调用密钥及授权，确认工作进程加载的是预期配置 |
| 503／部分来源失败 | 核对正式发布、日期覆盖、释放决定、站点字典、Yield 厂别和启用范围 |
| `read_timeout`／503 | 端口可用不代表业务读取已完成；按请求编号查 `API_READ_TIMEOUT`，核对首次加载、文件更新及 Office 耗时，可缩小产品／分类后重试 |
| CPK／CPM 503 | 核对公开政策、产品能力工作表、请求完整周及匹配的片号快照；必要时正常生成 SPC 报表或运行 5.6 同步，不把缺资料当成无不达项 |
| 请求超时／读取忙 | 看日志与并发使用情况，检查文件和 Office；不要快速无限重试 |

不要用假站点、统一修改全部释放标记或删除元数据来绕过不可用状态。错误反馈应包含时间、状态码及 `X-Request-ID`，不包含密钥。
