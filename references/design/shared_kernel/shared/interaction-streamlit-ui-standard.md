# Streamlit UI 交互与性能设计规范

生效日期：2026-11-16。适用于本项目 Streamlit 页面及其筛选、查询、图表、预警、下载和刷新交互。

本文是这些交互的通用规范。Agent 在开发、改造、排障或评审相关 UI 前必须阅读，按变更涉及的分支执行，并提供对应验证证据。项目硬边界及页面明确例外以 [CONTEXT.md](../../../../CONTEXT.md) 为准；业务算法、数据窗口和发布协议仍由各域文档拥有。既有 17 个页面的检查、整改及验收范围见 [页面符合性记录](../../../../docs/dev_docs/generated/shared_kernel/shared/ui-pages-compliance.md)，规范条文本身不替代运行验证。

## 1. 实施前先确定执行边界

在变更说明或用例中列出本次涉及的用户事件、允许执行的计算、重跑范围、状态失效条件与验证方式。小改动可直接写在交付说明中，不要求另建规划文件。

至少区分三种工作：

| 工作 | 例子 | 执行边界 |
|---|---|---|
| 产品或业务范围的数据准备 | 数据读取、点位制备、能力计算 | 按已选加载模式执行，服从既有缓存和版本策略 |
| 交互候选与结果选择 | 厂别限定站点、站点限定参数、筛选已有结果 | 通常允许在局部交互时执行；不因此重入无关的完整计算 |
| 图表构建与展示 | 对选中指标生成 Figure、绘制图像 | 服从该模块的查询或其他明确展示门控 |

**缓存决定计算能否复用；fragment 决定哪段代码重跑；查询门控决定何时取数或展示。三者必须分别设计。**

## 2. 加载模式与查询门控

### 2.1 两种允许的加载模式

| 模式 | 初次进入 | 修改筛选 | 点击查询 |
|---|---|---|---|
| 预加载并复用 | 准备完整业务范围输入及候选 | 局部更新候选和选择，复用已取得输入 | 选择已有结果并构建本次图表 |
| 提交后按需计算 | 独立取得必要候选，不运行完整结果计算 | 局部更新候选，保持完整计算未提交 | 对提交范围读取或计算结果，再绘图 |

两者都是有效设计。依据数据规模、候选来源及频繁切换条件的成本选择；已有明确产品设计时先保留。不得把“查询前存在计算”直接判为 bug，也不得以优化 UI 为由擅自改变业务取数范围。

使用公共页头产品筛选的页面先点击“查询”，再加载本页已提交产品的输入。此后整页重跑、刷新数据与刷新缓存均沿用该产品。SPC 的 `render_spc_report_interaction` 内的厂别、站点和参数查询复用已加载输入。

### 2.2 候选和结果的依赖要分开

- 级联候选必须能在结果查询前获得。优先复用已有指标清单；按需模式可通过独立的轻量目录取得候选。不要为了得到少量候选反复运行完整报表服务。
- 需要“厂别→站点→参数”即时级联时，使用局部重跑更新候选。普通 form 只在提交时传递输入，不适合直接承载这种即时依赖；独立输入适合用 form 批量提交。
- 点击查询应提交当前有效组合。组合、产品、时间范围或依赖版本变化后，按模块契约重新判断结果是否仍适用，不能把旧结果标成新条件的结果。
- 保留现有选择清理规则，例如厂别改变时清空下级，站点组合改变时重建参数候选。共享控件调整须检查所有实际消费者。
- 明确按钮究竟是“提交选择”“读取最新结果”还是“强制刷新源数据”。预加载模式下点击查询不会天然检查外层报表的源版本或 TTL；需要更新输入时必须有明确刷新路径。

## 3. Fragment 隔离和状态所有权

### 3.1 按独立交互范围划分

- 多独立业务模块页面：每个模块的筛选、查询、结果、空态和错误分支放入自己的 fragment，操作 A 不得重跑 B 的业务加载或重置 B 的已提交结果。
- 单业务模块但存在“完整预加载＋局部筛选”的页面：完整预加载与局部筛选也必须有执行边界。采用 fragment 时，把该组控件及其结果放在同一入口，完整产品加载留在其外部。
- 控件和结果由所属 fragment 创建并更新，默认写入自身容器。不要持续追加到外部容器；确需跨容器渲染时必须验证替换、清理和无重复元素。
- 页面配置、初始化、共享页头和组合根装配属于 `app/pages/`；模块交互入口属于 `app/sections/<domain>/<submodule>/`。按需模式的查询计算可在所属 fragment 的已提交分支调用应用服务。

不能只给结果函数加装饰器，却把触发它的筛选控件留在 fragment 外；也不能将整个页面的无关模块包进一个大 fragment，声称已经完成隔离。

### 3.2 Session State 与刷新

- Widget key、查询签名和图表标识按页面、模块、用途隔离，保留已被布局或其他消费者使用的稳定 key。
- 会话状态描述用户的选择与展示，不拥有其他模块的状态，也不替代共享计算缓存。
- 普通控件事件优先利用已经发生的局部重跑。默认 `st.rerun()` 会请求整页重跑，只能用于明确需要全页一致性更新的路径。
- 确需再次局部重跑时，`st.rerun(scope="fragment")` 只能在合法的 fragment 局部重跑上下文中调用，不能无条件进入首次整页路径。
- 跨模块产品、权限、配置或数据代次变更，必须通过明确的整页更新协调输入和结果；不要混用新代次数据与旧 fragment 捕获的输入，也不要期待修改其他模块状态会自动重绘它。
- 默认普通 `@st.fragment`。启用 `parallel=True` 前须证明依赖、数据库连接和共享资源线程安全；局部隔离需求不构成改变并发模型的理由。

首次整页运行仍会执行各 fragment。fragment 本身既不保证首次加载按需，也不保证并行，更不保证每个 UI 操作零开销。

## 4. 缓存、数据一致性与预警

- 保留应用层已有的缓存入口和刷新接口，使用参与结果的产品、窗口、源版本、配置及决策版本构造身份。容量与 TTL 使用项目已配置的机制。
- 数据缓存仅存 DataFrame、标量和原生容器；项目定义的 ViewModel 在缓存外构造。不要仅为掩盖整页重跑新增无界的会话级完整报表副本。
- 页头加载提示处于缓存外时，即使命中缓存仍会经过该调用。诊断时分别记录加载入口、缓存未命中、实际数据源访问和图表构建，不能把 spinner 次数等同于 SQL 次数。
- 查询和刷新按既有范围失效；不要用清空全局缓存解决单模块问题。共享刷新按 [页头更新机制](data-flow-page-header-refresh.md) 协调各模块。
- 已发布预警展示与原始分析分离，遵循 [预警展示契约](../../inline_domain/shared/architecture-published-alert-display.md)。局部筛选、缺少可选图像或结果缓存未命中，都不能成为擅自运行预警生产流程的理由。
- 普通 UI、下载、空态及异常分支遵守 CONTEXT 的非管理员展示边界；页面明确约定的提示例外继续有效。不要把读取失败伪装成空数据或零预警。
- 图表和导出消费已定义的数据契约，不在展示层重写业务事实。SPC 最终点位边界由 CONTEXT 和对应域文档维护。

缓存关闭、TTL 到期或后台数据更新后是否重新取数，必须在页面加载模式中有可说明的触发路径；不能假设局部重跑会自动刷新外层输入。

## 5. 图表构建、容量与布局

- 查询门控应放在它要阻止的昂贵操作之前。门控若只包住渲染，就只能声称阻止渲染，不能声称阻止了此前的取数或计算。
- 数据预加载不意味着预先构建所有指标的图像。默认对已提交或明确要求自动展示的范围构建图像，保持普通查询与自动预警的各自契约。
- 折叠面板、标签页默认不等于计算被跳过。需要按展开状态延迟执行时，必须有实际条件分支及验证，不能仅因内容不可见就宣称懒加载。
- 复用已有图表 memo 时纳入实际输入版本；数据或规则改变后不得继续展示旧 Figure。有限会话图表复用不能代替共享数据缓存。
- 同时显示大量图表时检查全部展开后的容量、窄屏布局与浏览器错误。多个独立 WebGL 图可能耗尽上下文；应按实际图量选择 SVG、复用或延迟绘制，并验证可见图表没有被回收。

Q-Time 单腔图的具体图形类型、点位和规格口径仍属于该模块，不推广成所有报表的统一业务规则。

## 6. 页面滚动与 Plotly 交互

长报表的普通滚轮优先用于页面纵向浏览。对于现有 SPC、CTQ、AOI_TT、AOI_RS 报表，普通图表与预警图在 `st.plotly_chart` 渲染入口显式保留 `config={"scrollZoom": False}`；新增配置项须合并，不能覆盖此项。

- 保留工具栏缩放、坐标重置、平移及既有拖拽能力，不通过静态化图表或禁用全部鼠标事件修复滚动。
- 按页面确定主滚动容器；不要未经验证全局修改 `html/body`、固定报表高度、隐藏滚动条或新增嵌套结果滚动框。
- SPC 已有浏览器文档自然滚动的页面特例，作用域由 `.st-key-spc_factory_filter` 限定。保留初始化及作用域，控件 key 改名须同步检查 CSS；不得将特例自动扩展到其他页面。
- 调查滚动故障时分别检查图表滚轮处理、实际溢出容器的高度与 overflow、覆盖层及大量绘图导致的无响应。不能只看到外层容器 `overflow: hidden` 就认定页面锁定。

SPC、CTQ、AOI_TT、AOI_RS 的现有图表入口分别为各自 `app/sections/inline_domain/<子模块>/` 的 dashboard 文件；SPC 的页面特例由 [scroll_layout.py](../../../../app/sections/inline_domain/spc/scroll_layout.py) 维护。其他 Plotly 工具若需独立滚轮缩放，应在其页面契约中明确范围并验证，不套用为全项目 CSS 或事件拦截器。

## 7. 交付前验证门槛

只执行本次变更涉及的项目，但每个涉及项都要有结果和证据；未覆盖项必须明确说明。

| 涉及行为 | 必须验证 |
|---|---|
| 局部重跑 | 用真实浏览器操作，分别记录页面、各模块、完整加载入口、查询和图表构建次数；局部事件不增加无关加载，整页刷新作为正向对照仍能增加 |
| 级联与查询 | 上级变更后候选及旧选择正确更新；未提交结果不冒充新条件；有效查询可绘图，重复查询、产品或版本变更按契约处理 |
| 多模块 | A 的操作保留 B 的选择和已提交结果；无重复控件、累计输出或旧下载内容；共享刷新可协调全部受影响模块 |
| 缓存与输入更新 | 区分入口重跑与实际重算；验证刷新、代次变更及错误回退，不混用新旧输入，不靠加长 TTL 隐藏问题 |
| 状态与公开展示 | 正常、空数据、初始化失败和结果构建失败；公开表格、列菜单、hover 与导出满足 CONTEXT；按页面例外处理提示 |
| 滚轮与布局 | 多指标、全部相关展开区域、窄屏；鼠标在空白区及各类图表上向下和向上滚动，文档或指定主容器位置改变，图表坐标不随普通滚轮变化 |
| 图表工具与导航 | 工具栏缩放、重置、平移仍有效；主滚动条可拖动；离开 SPC 后其 CSS 不作用于其他页面 |

AppTest 可检查筛选、查询门控、空态和 fragment 归属，但当其运行器请求整页执行时，不能用其重复调用计数代替浏览器 WebSocket 的 fragment 隔离验收。配置断言也不能代替实际滚动测试。

浏览器证据只放在 `output/test-results/` 或 `output/tmp/`。优先无数据库、隔离输入的测试页面；按全局约束记录并清理本任务创建的测试进程及端口，验证退出和监听释放，保留正式服务。历史成功记录、夹具计数和模拟滚动锁定均不得冒充本次生产验收。

## 8. SPC Bug 与旧规范的关系

| 可核实事实 | 结论 |
|---|---|
| 原 SPC 在完整加载之后才执行查询展示门控，筛选控件没有局部重跑边界 | 筛选事件会再次进入完整加载入口；门控无法跳过已经执行的前置代码 |
| 旧 fragment 文档明确面向同页多个独立业务模块，实例为 Q-Time | SPC 单业务模块的预加载加局部筛选不在旧文档的明确适用范围，不能简单认定违反了一个直接适用条款 |
| 旧设计要求独立交互不带动无关执行，SPC 后续通过 fragment 隔离修复 | 同类隔离原则没有在 SPC 落实；本规范现已明确覆盖多模块与单模块预加载两种场景 |
| 本次整理前（2026-11-16）的知识索引未直接路由到多模块 fragment 文档，滚动文档路由仍指向迁移前路径 | 当前路由存在发现性缺口；这不证明 bug 发生时路由也相同，更不能推断某个 Agent 当时读过或故意忽略了规范 |

**机制归因为执行范围隔离不足，不是“预加载本身错误”，也不能推断每次都重新查询数据库。** 本次另确认规范适用范围及当前读取路由存在缺口，现一并补齐；这些文档缺口不能直接当作已证明的历史发生原因。

SPC 当前实现见 [独立交互入口](../../../../app/sections/inline_domain/spc/spc_dashboard.py)；详细业务执行链见 [SPC 数据流](../../../domain/inline_domain/spc/data-flow-spc.md#53-建立级联筛选与查询门控)。本节是机制归因，不是对全部历史页面做过审计的声明。

## 10. 已合并的历史机制与证据

原三份独立说明已按用户要求删除，通用约束以本文为唯一入口；以下保留诊断所需的事实边界。

- **筛选重复加载**：普通控件原先触发整页脚本，先执行加载入口和外层 spinner，再判断当前筛选是否提交。位于下方的展示门控无法跳过前面已执行的代码。缓存命中也不等于加载入口、签名检查或反序列化没有执行。2026-11-13 的隔离浏览器中，首次加载计数为 1；改变站点、参数、厂别和重复查询均保持 1，显式整页刷新后变为 2。相关回归当时为 127 项通过，不代表本轮审计的测试数量。
- **滚轮与滚轴是不同问题**：2026-09-09 确认过 Plotly 滚轮缩放配置缺口；2026-11-03 的 SPC 间歇滚轴问题发生时，配置和运行时已为 `scrollZoom=False`。后者采用限定 SPC 的文档自然滚动防护，不能仅凭相似现象认定相同根因。
- **SPC 原生滚动证据**：2026-11-03 无数据库夹具验证了单参数三图、多参数 33 图、普通及管理员、空数据、失败和非 SPC 页面等 7 个场景；单参数及多参数文档高度分别为 1413px、8198px，视口为 1000px。当时 52 项定向测试通过。负向对照模拟的是内部 `stMain` 禁止滚动，不等于稳定复现了用户原标签页的间歇根因。历史证据路径为 `output/test-results/spc-scroll/document-scroll-verification.json`，运行时产物可能按生命周期清理。
- **多模块案例**：Q-Time 的 `qtime_` 和 `chamber_` 状态各自归所属 fragment，页头共享刷新留在外层。站间保存后只在合法局部重跑上下文使用 `st.rerun(scope="fragment")`，更新下载和图像；产品、配置和跨模块代次变化仍协调整页刷新。业务专有点位、规格、图形类型和提示例外不由 UI 范式重定义。
- **工具证据边界**：原滚动验收曾发现滚轮工具事件可能落在 `(0,0)`，不能假设沿用前次鼠标位置。应核对实际事件坐标，必要时在明确坐标发送原生滚轮；缓存或 CSS 的单元测试不能代替现场滚动。
