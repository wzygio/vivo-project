# 0044 — 全指标独立自动巡检

日期：2026-11-12。状态：已实现并验证；本地开发分支 `feat/alert-notification`。

## 背景

自动预警页面和HTTP消费已发布结果，不能保证无人访问时各领域仍产生新结果。
旧独立任务只覆盖Yield/IJP，API消费范围也小于自动看板。用户要求覆盖完整看板、
迁移巡检实现到api、统一每日生产并配置两次周度邮件。

## 决定

- 新增 `api.inspection`，统一10个业务生产模块，覆盖13个看板指标，
  并生产AOI两类趋势与API使用的OOC。领域application/core保留算法所有权。
- 调用真实仓储刷新和现有发布流程；强制只读数据库会话和有限超时。
  生产入口核对本轮来源、覆盖、规格和落盘代次；不以旧空表作为完成证明。
- 完整启用产品范围和全部厂别执行，模块失败隔离，串行降低数据库与Office争用。
  现有人工flag、维护台账和源快照生命周期继续保留。
- 新增原子巡检回执，验证准确模块／产品清单，记录活跃进程身份；
  预警邮件等到当天全部必需生产完成后再读取API，避免07:15→07:20的调度竞态。
- API HTTP请求继续只读。没有新增触发生产的HTTP端点，也不依靠浏览器自动访问。
- 原工具脚本成为薄兼容入口；原30分钟任务改为每日07:15，邮件任务每周触发为
  周一07:20和周二11:00。登记前备份精确目标任务定义，登记后核对实际动作与触发器。

## 取舍与后果

不为每类事件复制计算引擎；SPC一次报表生产同时产生四类事件和成员，
同产品SPC／CTQ／TT复用源刷新，RS保留独立来源，Q-Time按全部厂别处理。
生产和发信为独立命令，消费方不会自行补算；部分失败时任务可继续其它来源，
但邮件完整性门禁失败，不把剩余数据冒充完整周报。

当前Windows任务使用已登录账户、隐藏pythonw进程。开机、登录、数据库网络、
Office受保护文件权限和SMTP可用性仍是运行前提；不承诺注销／关机时运行。
每日刷新成本高于仅读取结果，因此需要依据真实全产品运行耗时验证任务上限。
SMTP接受仍不能替代邮箱端收件证明，自动邮件不重试不确定投递。

真实验收还要求辨别成功空结果和来源失败。备件原生查询在完成取数与处理后签发
本次调用的完成证明，旧快照与异常回退不能签发；巡检同时核对发布时间和产物。
备件来源保持原时间窗口和匹配范围，在数据库端先排除无效数值，再按原键选择最新值，
减少历史行传输；不缩短查询窗口，也不放宽巡检超时。
受保护工作簿的读取仅对已知瞬时读取错误重试一次，缺规格、错误表结构及来源变化
仍然失败。SPC成员签名变化时，只有逻辑策略、原生日期覆盖与来源代次均未改变，
才允许用同一轮计算点集重新发布成员快照；不修改HTTP消费策略。
