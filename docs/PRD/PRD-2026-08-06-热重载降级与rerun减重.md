# PRD：热重载降级为手动 + 页面 rerun 减重

- 日期：2026-08-06
- 状态：待评审（未实施）
- 关联页面：`app/pages/SPC监控报表.py`（所有页面共用 `render_page_header`，影响面为全站）
- 关联代码：`app/components/page_header.py`、`app/utils/reloader.py`、`app/sections/spc/spc_dashboard.py`、`src/inline_domain/application/spc/spc_service.py`

## 1. 背景与问题

SPC 监控报表的"厂别"筛选框需要连续点击约三次才能切换成功：前两次点击后
选项回退到默认值（ARRAY），并伴随长时间加载/卡顿。

### 1.1 已完成的排查结论（事实依据）

1. **筛选组件代码无 bug**。用与生产相同的环境（uv 锁定 Streamlit 1.60.0）实机
   驱动浏览器点击 4 次，全部一次成功（含一次恰好触发 Deep Reload 的点击）。
   `render_spc_filters` 的状态写法规范，唯一重置入口（spc_dashboard.py:226-227）
   不可能误触发。
2. **会话/页面被反复重置**。`output/logs/app.log_info.log` 显示 2026-08-06
   14:25:43~14:27:23 间 4 次完整配置加载，而 `config/*.yaml` 自 7 月以来未改动
   ——session_state 被反复清空（新 session），所有筛选 widget 回到默认值 ARRAY。
3. **热重载风暴**。`get_project_revision`（app/utils/reloader.py:29）把
   `resources/**/*.xlsx/csv` 的 mtime 纳入代码指纹；应用每次重建 payload 都会重写
   `resources/<prod>/spc_sheet_oos_*.xlsx`、`spc_cpk_*.xlsx`（mtime 已验证更新），
   企业加密软件也会异步触碰 xlsx。指纹不稳定 → `setup_hot_reload`
   （page_header.py:242）在页头 `st.rerun()` 打断当前 run 并卸载约 93 个模块。
   日志实测：14:55:04~14:55:06 两秒内 3 次 Deep Reload。
4. **每次 rerun 过重**。payload 约 80 万行 × 多个 DataFrame，每次 rerun 都要过
   `st.cache_data`（`max_entries=1`，多标签/多产品互相驱逐会触发 30~90s 全量重建）；
   自动预警图像在每次 rerun 都重建。run 越长，用户点击与页面重置踩踏的窗口越大。

### 1.2 问题定义

- P1（本 PRD 解决）：热重载自动 `st.rerun()` 打断用户操作、放大每个 run 的耗时
  与不确定性。
- P2（本 PRD 解决）：每次 rerun 的重计算量过大，点击响应慢。
- P3（本 PRD 不解决）：会话重置的环境因素（多标签页、频繁 F5、企业安全软件干预
  localhost websocket——日志中存在 `ConnectionResetError`）。P1+P2 落地后若仍
  复现，再专项排查。

## 2. 方案 A：自动热重载降级为手动热重载

### 2.1 用户决策约束

- 保留对 `.py` / `.yaml` 的监控（`get_project_revision` 的追踪范围不变，
  `.xlsx/.csv` 也维持现状——降级后它只驱动"提示"，不再驱动"打断"，误报无害）。
- 将三项能力全部收进页头"🔄 刷新缓存"按钮：**缓存刷新 + 代码重载 + 配置文件重新读取**。

### 2.2 现状

`render_page_header` 开头调用 `setup_hot_reload()`：发现文件变更 →
`deep_reload_modules()` + `st.rerun()`，当前 run 在页头处被中止。

"刷新缓存"按钮（`_hard_reset_callback`，page_header.py:141）现状：
失效产品缓存 → 清 session_state 视图缓存 → **仅全量模式**做 `deep_reload_modules()`
→ 清页面级签名。不做配置文件重读（配置热重载目前依赖
`SessionManager._needs_reload` 的 mtime 轮询）。

### 2.3 目标设计

**被动检测（每次 rerun 执行，无副作用）**

`setup_hot_reload` 改造为纯检测：

- 计算 revision 并与 `st.session_state['last_code_revision']` 比对；
- 一致：清除 `code_update_pending` 标记以外的动作一概不做；
- 不一致：仅置 `st.session_state['code_update_pending'] = True` 并更新
  `last_code_revision`，**不卸载模块、不 `st.rerun()`**；
- 页头控制栏根据 `code_update_pending` 渲染提示（如"刷新缓存"按钮旁显示
  `st.caption("⚠️ 检测到项目文件变更，点击「刷新缓存」应用")`）。

**手动应用（点击"刷新缓存"时执行）**

`_hard_reset_callback` 扩展为固定四步：

1. `deep_reload_modules()`——卸载 `src`/`app` 后端模块（从仅 global 分支提升为
   总是执行；产品作用域页面同样需要代码重载）；
2. `SessionManager.load_and_set_config(当前产品)`——强制重读
   `config/global.yaml` + `config/products/<prod>.yaml`；
3. 原有缓存失效逻辑不变（产品作用域 bump revision / 全量模式 func.clear()、
   清视图缓存与签名）；
4. 清除 `code_update_pending` 标记。按钮点击天然触发 rerun，**不额外调用
   `st.rerun()`**，页面以新代码 + 新配置 + 已失效缓存完整重执行。

### 2.4 可行性分析

- Streamlit 按钮 `on_click` 回调在下一次脚本执行前运行；回调内卸载
  `sys.modules` 中的 `app.*`/`src.*` 后，脚本主体重新 `import` 即获得新代码——
  机制与现有 global 分支相同，已在生产使用。
- 页面模块（`app/pages/*`）由 Streamlit 每次从源码重新执行，不受 sys.modules
  卸载影响。
- `@st.cache_data` 的缓存 key 由模块名+限定名构成，模块重载后 key 稳定；且产品
  revision bump 保证必 miss、用新代码重建，不会出现"新代码跑旧缓存"。
- `setup_hot_reload` 仅 `render_page_header` 一处调用（page_header.py:95），
  改动收敛。

### 2.5 风险与缓解

| 风险 | 等级 | 说明与缓解 |
|---|---|---|
| R-A1 行为变化：改代码后页面不再自动生效 | 中 | 这是本次降级的预期代价。缓解：页头出现"检测到变更"提示；更新开发文档说明新流程（改代码 → 点刷新缓存）。 |
| R-A2 被动检测仍每次遍历 stat 全部受追踪文件 | 低 | 与现状成本相同，无新增开销。 |
| R-A3 回调中卸载模块后当前 run 残留旧引用 | 低 | 回调先于脚本主体执行，主体全部重新 import；现有 global 分支已验证该模式。 |
| R-A4 配置重读失败（yaml 损坏）导致页面中断 | 低 | `load_and_set_config` 内部已 `st.error` + `st.stop`，与现有产品切换路径一致。 |

## 3. 方案 B：每次 rerun 减重（详解与风险评估）

### 3.1 B1：自动预警图像构建结果 memo

**现状**：`render_cpk_alert_indicator_sections` 在页面中的调用位置
（SPC监控报表.py:119-125）位于"是否已查询"判断之前，**每次 rerun 无条件执行**。
RenderGate 改造后，每次 rerun 都会在 spinner 下重新构建全部预警指标的 Plotly
Figure（这是页面除 payload 外最大的重计算块）。用户每点一次筛选框，都要等这批
图全部重算一遍，尽管数据根本没变。

**方案**：对"预警图表 payload 构建"做 memo，渲染（`st.*` 调用）仍每次执行：

- 存储：`st.session_state["spc_alert_charts_memo"] = (signature, payload_list)`。
  选 session_state 而非 `st.cache_data`，因为后者会对入参大 DataFrame 做哈希/
  序列化，成本可能超过构建本身；session_state 手动 memo 零序列化、完全可控。
- 签名：`build_product_cache_signature(...)`（含产品缓存 revision）+
  `alerts_df` 廉价指纹（行数 + 关键列值 tuple）。构建前比对签名，一致则直接复用
  payload_list 进入渲染阶段，不一致才走 RenderGate 构建。

**为什么安全**：点"刷新缓存"必然 bump 产品 revision → 签名必变 → 必重建，
不存在"数据更新了图没更新"的路径；同一 session 内数据不变时签名稳定，命中 memo。

| 风险 | 等级 | 说明与缓解 |
|---|---|---|
| R-B1-1 签名碰撞导致旧图 | 低 | 签名包含产品 revision（手动刷新必 bump）与 alerts 内容指纹；理论碰撞窗口只剩"数据原地变化但 alerts 行数与取值完全相同"，无实际场景。 |
| R-B1-2 内存占用 | 低 | 预警指标通常个位数，Figure 对象 KB~MB 级。 |
| R-B1-3 与 RenderGate 语义冲突 | 低 | memo 命中时跳过 stage/collect 直接渲染；未命中时维持现有两阶段行为。 |

**收益**：筛选点击的 run 时长从秒级降到亚秒级，直接缩小 P3 踩踏窗口。

### 3.2 B2：`max_entries` 从 1 调大

**现状**：`fetch_spc_report_payload`（spc_service.py:170）是进程级全局缓存，
`max_entries=1`。同一服务进程开两个标签页（或一切换产品），两个 key 互相驱逐，
**每次 rerun 都是 30~90s 全量重建**（含 DB 拉取、装饰文件重写——又反过来喂大
热重载指纹波动）。

**方案**：`max_entries=1 → 3`，覆盖"当前产品 + 最近两个产品/标签"。

| 风险 | 等级 | 说明与缓解 |
|---|---|---|
| R-B2-1 内存峰值 = payload × 条目数 | 中 | payload 反序列化后单产品估计数百 MB（80 万行 × 多表）。实施前实测 `sys.getsizeof`/pympler 定量，若单条 >300MB 则降为 2。 |
| R-B2-2 多标签共享导致旧数据停留更久 | 低 | 缓存失效仍由 revision bump 保证，与条目数无关。 |

**收益**：仅限多标签/频繁切换产品场景；单标签无收益也无代价（除内存）。

### 3.3 不做的事

- 不改动筛选组件逻辑（已证明无 bug）。
- 不调整 `get_project_revision` 的追踪扩展名范围（用户决策保留）。
- 不处理 P3（websocket/多标签/F5 等环境会话重置）。

## 4. 实施计划

1. `app/components/page_header.py`：`setup_hot_reload` 改为被动检测 +
   `code_update_pending` 标记 + 页头提示；`_hard_reset_callback` 增加
   `deep_reload_modules()`（提升为总是执行）与 `SessionManager.load_and_set_config`。
2. `app/sections/spc/spc_dashboard.py`：`render_cpk_alert_indicator_sections`
   增加 session_state memo（签名命中跳过构建）。
3. `src/inline_domain/application/spc/spc_service.py`：`max_entries` 调整
  （先实测 payload 内存再定 2 或 3）。
4. 测试：
   - 新增/更新单测：被动检测不 rerun、标记置位与清除、手动回调四步顺序、
     memo 命中/未命中路径。
   - 运行 `tests/unit/app/`、`tests/unit/app/pages/` 全量。
5. 实机验收（Playwright，与本次排查同法）：
   - 厂别单击一次切换成功，连续切换 5 次无回退；
   - 修改任意 `app/` 下 .py → 页面不自动 rerun、出现提示 → 点刷新缓存后新代码生效；
   - 日志中除手动刷新外无 Deep Reload 记录。

## 5. 验收标准

- 厂别/站点/参数筛选单击一次生效（自动化脚本验证）。
- 日志中不再出现非手动触发的 `Deep Reload`。
- 代码变更不再自动打断页面，提示与手动生效路径可用。
- 既有测试全绿，无布局/交互回归（widget key、st.* 调用顺序不变）。

## 6. 开放问题

- P3 会话重置的环境因素（多标签、F5 习惯、企业安全软件）需用户侧确认；
  A+B 落地后观察日志 1~2 天，若仍出现非预期 session 重建再专项处理。
- payload 内存实测结果决定 `max_entries` 取 2 还是 3。
