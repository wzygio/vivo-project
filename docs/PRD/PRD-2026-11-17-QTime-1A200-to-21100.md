# 重点站点 Q-Time 新增 1A200 → 21100 路径

- 日期：2026-11-17
- 状态：固定路径取数与原报表接入已实现；验证与交付结果见本文件末尾及专项交付记录。未部署或重启正式服务。
- 目标页面：[Q_Time监控报表.py](../../app/pages/Q_Time监控报表.py) 中的“重点站点QTime监控”。
- 参考文件：[Z016_Search_QTime_Monitor_By_Lot.cpt](../project_files/indicator_domain/qtime/Z016_Search_QTime_Monitor_By_Lot.cpt)。
- 需求澄清后，用户已授权开发直至 E2E 通过；2026-11-17 已完成只读元数据、有限样本与原监控服务的真实数据核验。
- 范围澄清：用户明确要求，CPT 仅作为取数、关联与去重的参考。补充数据输出到当前报表标准输入后，所有后续逻辑沿用当前报表；不开发通用站点组合能力，不另设返工规则或预警展示规则。

## 1. 评估结论

**方案在逻辑和现有报表接入契约上可行。新增范围只限于补取 `1A200 → 21100` 这条固定路径的源数据，并整理成当前报表要求的输入字段；之后直接进入现有监控用例。**

依据如下：

1. CPT 已使用 `DWR_MES_LOT_HIST.LOT_ID`、`OPER_CODE`、`EVENT_TIME` 和 `EVENT_NAME='TrackIn'`，具备批次、站点、进站时刻的字段依据。
2. CPT 的 `DWR_MES_LOT_HIST` 仅用于补充已有 Q-Time 主记录的目标进站时间。主记录不存在时，原 SQL 不会自动构造 `1A200 → 21100`。
3. 当前 Python 站点报表读取 `mdw.qtime_tzbjx` 的成品明细。由于该源没有新路径，仅修改站点选项或规格配置无法补出数据，需要为这条固定路径补充取数。
4. 将补充数据转换成现有明细结构后，可以复用规格准备、三态人工决策、确定性修饰、展示限幅、图表、缓存和正常预警发布流程。
5. 用户补充的 `mdw.dwr_mes_productspec` 关联可用于把事件携带的产品规格标识映射到报表产品代码，但事件源中的具体关联列、映射唯一性及有效期仍需核验。

这里的“可行”不代表已经确认生产库中存在两站的完整 TrackIn 履历，也不代表已经验证应用账号能够读取这些对象。

## 2. 已确认需求与本次范围

### 2.1 已确认事项

| 项目 | 要求 |
|---|---|
| 新增路径 | `1A200 → 21100`，站点代码按字符串处理，保留字母和前导字符 |
| 时间口径 | 用户明确选择“两站进站时间之差” |
| 计算公式 | `wait_time = (21100进站时间 - 1A200进站时间).total_seconds() / 3600` |
| 最小取数信息 | `lot_id`、进站时间、`step_id` |
| 站点字段映射 | CPT 中对应字段为 `OPER_CODE`，不是已经确认存在的数据库列 `step_id` |
| 产品映射 | 通过 `mdw.dwr_mes_productspec` 的 `productspecname` 与事件侧产品规格值关联，读取 `productcode`；示例目标为 `M626` |
| 后续全部处理 | 数据整理为当前报表标准输入后，规格处理、人工决策、修饰、展示限幅、图表、统计、预警、缓存和发布继续沿用当前报表 |
| 去重等取数细节 | 以 CPT 生效的关联、排序及 `ROW_NUMBER()/RN=1` 为参考；仅用于源数据提取，不将 CPT 的后续处理搬入 Python 报表 |
| 规格 | 用户稍后提供；本阶段不设定数值规格，不从其他路径借用规格 |

产品关联字段的准确拼写为 **`productspecname`**；用户提供的关系是 `p.productspecname = sta.product_spec`，其中 `sta` 是事件侧别名，不是本次已经核验的物理表名。

### 2.2 范围

本期新增设计仅覆盖取数侧：固定路径的进站履历读取、同批次记录关联、参考 CPT 的去重、产品识别，以及转换为现有报表输入。站点选项需要识别新增来源，其余页面和业务规则沿用当前实现。

不包含：任意站点组合的通用查询能力、新的返工分段/终点复用规则、无规格专用预警旁路、预警分母调整、新的图表规则、修改 MES 或数仓数据库、生成不存在的进站事件、杜撰规格、复刻 CPT 的状态管理界面，以及改变蒸镀单腔监控算法。

此前“配对”仅应理解为：在取数时，按同一 `lot_id` 关联 `1A200` 和 `21100` 的进站记录，以便准备报表需要的时长字段。它不是取数完成后的另一套业务处理流程。

## 4. 来源与字段契约

### 4.1 候选事件来源

以 CPT 引用的 `DWR_MES_LOT_HIST` 为来源，分别提取两个站点的 `TrackIn`。CPT 本身只配置连接名 `gp_conn`；本次另经应用数据库只读元数据确认实际对象为 `mdw.dwr_mes_lot_hist`，且可读取。

| 业务字段 | CPT 已证明的来源 | 规范化字段 | 核验事项 |
|---|---|---|---|
| 批次 | `LOT_ID` | `lot_id` | 非空、两站标识是否一致，是否存在拆并批 |
| 站点 | `OPER_CODE` | `step_id` | 精确匹配 `1A200`、`21100`，不按数值转换 |
| 进站时刻 | `EVENT_TIME` | `entry_time` | 数据类型、时区、精度及其业务含义 |
| 事件类型 | `EVENT_NAME` | `event_name` | 仅 `TrackIn`；TrackOut 不作为本路径时间端点 |
| 源厂别 | `FACTORY` | `source_factory` | 两端分别确认，不能要求起点、终点厂别相同 |
| 产品规格标识 | 本次元数据及样本确认 `prod_id`、`prod_ver` | 用作用户示例的 `product_spec` 及版本 | 按起点产品规格、版本、厂别映射，避免不同版本和厂别放大记录 |
| 事件排序信息 | 本次元数据确认 `event_timekey` | 内部排序信息 | 时间相同时辅助稳定排序；最终仍检查原报表秒级四键是否冲突 |

如果同一 Lot 在两站之间更换 Lot ID，不能直接用前缀、截断或模糊匹配补齐。须另行验证可追溯的批次谱系关系；缺少该关系时，只处理两端 Lot ID 一致且可验证的样本，并记录覆盖缺口。

### 4.2 产品识别：采纳用户补充关系

映射关系为：

```text
事件侧 product_spec
    = mdw.dwr_mes_productspec 的 productspecname
    → mdw.dwr_mes_productspec.productcode
    → 当前报表标准列 prodcode，例如 M626
```

准确的关联条件是 `p.productspecname = sta.product_spec`；用户示例中的 `p.productcode = 'M626'` 为单产品验证条件。正式能力应支持全局启用产品集合，不能将所有事件硬编码为 M626。

要求：

1. 以该次起点事件的 `prod_id`、`prod_ver`、`factory` 识别产品，分别关联主数据名称、版本和厂别；身份缺失时拒绝该次来源，不用当前 Lot 属性或批次前缀猜测产品。
2. 同一规格到相同 `productcode` 的重复主数据先去重；一个规格对应多个不同有效产品代码时，按核实后的版本/业务有效期处理。不能任取一条、复制成多个产品，或直接关联导致事件行数膨胀。
3. `EXISTS` 适合验证某产品成员关系；多产品输出需要明确取得唯一映射的 `productcode`，不能把 `SELECT 1` 当作产品名称输出。
4. 无匹配或有歧义的记录不冒充正常产品数据；单独记录数量、原因和数据覆盖状态。相关源读取失败与“确认没有匹配”须区分。
5. 映射结果投影到现有 `prodcode`；筛选、缓存、图表按启用产品代码使用它。源规格值保留于内部追溯字段，不覆盖既有产品标签配置。

### 4.3 统一输出到当前站点报表

| 标准字段 | 新路径的来源或约定 |
|---|---|
| `lot_id` | 两端匹配后的真实批次 |
| `f_step` / `t_step` | 固定字符串 `1A200` / `21100` |
| `step_desc` | 建议使用唯一、稳定的 `1A200->21100`；不得随显示文案变化，避免人工决策失配 |
| `shop` | 按现行起点前缀归类为 `ARRAY`；此展示归类不等于两端源 `FACTORY` 必须都是 ARRAY |
| `prodcode` | 上述主数据映射得到的启用产品代码 |
| `wait_time` | 两站进站时刻差，单位小时；按源精度计算后再格式化显示 |
| `q_spec` | 当前为空值；不能填 0、无穷大或借用别的路径规格 |
| `timekey` | 使用起点 `1A200` 进站时间，与 CPT 的起点分组一致；真实样本存在多个起点共用终点，终点不能唯一标识现有决策键 |
| `prod_qty` | 使用已核验起点履历的真实 `prod_qty`；不能把事件行数或固定批量当作产品数量 |
| `sub_prod_type` | 有经核实的批次属性来源才填，无可靠来源时为空 |
| 内部追溯信息 | 取数诊断可保留两端源进站时刻、厂别、规格和来源标识；不因此扩展公开明细或现有人工决策键 |

补充取数在进入 `_normalize_source_details()` 和现有应用用例前完成字段适配。交付边界是当前 `DETAIL_COLUMNS` 及现有源时间精度契约；不要求为新路径重新设计下游的数据结构。

## 5. 取数侧的同批次关联与去重

本节仅描述数据提取，不新增取数之后的业务规则。

1. 限定站点为 `1A200`、`21100`，事件类型为 `TrackIn`；两端厂别按真实源字段分别核实。
2. 按同一 `lot_id` 关联起点和终点进站记录，补充产品映射，取出两次进站时刻。
3. 参考 CPT 的生效去重方式：按批次、产品标识和起点时间分组，对目标进站时间升序编号，取 `RN=1`。CPT 的 `PROD_ID/ENTER_TIME` 在新取数中应对应经过核实的产品标识和 `1A200` 进站时间，而不是盲目复用列名。
4. 本需求不另外增加“终点必须在下一起点之前”“一个终点不得被重复关联”等返工规则，不建设可配置的通用事件关联引擎。
5. 按用户确认的两站进站时间差准备 `wait_time`，并一次性输出当前报表所需字段；数据来源中的重复不得放大为额外产品或时长记录。
6. 缺少必要时刻时，不用 `NOW()`、0 或其他批次补值。若有界样本发现负时长、无法区分的重复或与现有四键冲突，记录具体证据，先说明取数口径问题，再决定必要调整；不能自行添加另一套返工业务规则。

实际源没有对应 Q-Time 主记录，因此不能原样执行 CPT 主查询；需要调整的只是固定路径的取数来源及字段对应关系。CPT 的规格引用、状态分区或平台展示逻辑不迁入现有报表。

## 6. 时间窗口、数据安全与可验证性

### 6.1 核验后的显示锚点与有界取数

- 沿用当前监控窗口：上月 1 日至报表日次日零点的半开区间，并应用现有当日截止政策。
- 真实样本发现不同起点可能共用终点，故标准 `timekey` 采用起点进站时间，保留 CPT 的起点粒度；微秒在源标准化时保留，公开键沿用秒级。
- 两站均在原报表反算得到的源窗口内有界读取，仅输出已取得两个时刻的记录。起点在窗口外的记录不进入这个起点时间窗口，不宣称提供任意历史追溯。
- 普通增量刷新时，对补充路径重读当前整个源窗口，以补入较早起点后来才出现的终点；仅原成品源沿用原尾部增量读取。合并前整体替换该固定路径，不重复叠加旧片段。
- 原始两站时刻保留源时间，先计算时长，再在基础设施输出处对记录时间应用现有日期前推、截止及 Indicator 日期排除。不能将一个端点前推、另一个保持源时间后相减。
- 两站原始记录不因展示日期排除提前删除；先完成取数关联，再按起点时间的显示锚点应用原有输出过滤。

### 6.2 实施前只读核验顺序

1. 检查系统目录元数据，确认对象实际 schema、类型、列、权限、时间字段，以及视图的底层来源。
2. 通过统计元数据估算规模、分区/索引和预估代价；不用无界 `COUNT(*)` 或 `EXPLAIN ANALYZE` 代替规模探查。
3. 对所有有时间列的来源施加有业务意义的时间条件：两端履历分别有界；若另读 Lot/产品请求来源，也须分别有界；产品主数据按其有效期或截至时点约束。
4. 产品主数据不能为凑时间谓词而只保留最近更新行，导致仍然有效的旧规格漏映射。仅确认来源没有任何时间列后，才可豁免时间条件。
5. 从短时间窗口、限定列、限定站点和有限返回行数的样本开始，核验 M626 的映射与两站交集，再扩展到其他启用产品。所有条件使用绑定参数，设置超时、批量和容量上限。
6. 触及容量上限时显式失败或分批完成，不能截断后声称覆盖完整；关联前后记录数量用于检查重复放大。

全程只读，不修改数据库结构或数据，不使用任何临时表。CPT 中未对 LOT_HIST 加日期条件、PROP 的日期过滤被注释等细节不作为本项目的查询豁免。

## 7. 保持当前修饰与预警语义

**本节是现有逻辑的复用说明，不是新增功能设计。固定路径的标准数据输出之后，不再执行 CPT 的处理流程，也不新增该路径专属的下游分支。**

### 7.1 统一执行顺序

```text
既有 Q-Time 成品明细 ──────────────┐
                                  ├→ 标准化厂别事实/同一输出时间政策
固定路径取数 → 产品映射/关联/去重 ─┘
  → apply_qtime_spec_overrides
  → apply_qtime_decoration
  → details 的既有 constrain_qtime_display
  → 图表
  → 从 decoration 选 flag=False 的告警 → 正常发布 → 共用只读消费
```

旧路径保持原来源、原口径。补充来源仅服务本次固定路径，不作为其他路径缺数据时的自动替代源。

### 7.2 规格尚未提供阶段

- 当前先明确取数与字段契约，不要求用户立即提供规格。
- 没有规格来源时，`q_spec` 保持缺失，不杜撰数值；该输入继续由原服务、原修饰函数和原图表处理。
- 隔离验证确认：当前实现对空规格不会生成超规候选、规格修饰或规格线，时长仍可绘图。这是既有行为，不是新路径专用逻辑，也不是已经完成真实规格判定的证据。
- 原预警中心、空表状态、统计分母及发布规则全部沿用，包括 ADR-0036 的既有约定；本需求不新增无规格预警旁路、不重定义状态或成功文案。

### 7.3 用户提供规格后的行为

继续使用现有规格准备入口，按产品、起点、终点的约定粒度关联；规格具体数值和产品差异本 PRD 不预设。若各产品不同，不可仅用厂别/路径级覆盖值冒充产品级规格。

| 当前规则 | 新路径接入要求 |
|---|---|
| 超规识别 | `q_spec > 0` 且 `wait_time > q_spec`，不另建判断公式 |
| 未命中台账 | 当前超规候选默认 `flag=True`，保持既有行为 |
| `True` | 复用按四键与规格生成的稳定修饰值 |
| `False` | 真实超规证据进入预警；展示明细仍遵循既有独立限幅开关 |
| `Delete` | 从报表明细排除，不回写删除源履历 |
| 展示限幅 | 生产配置当前为 `constrain_display: true`，命中后落入规格约 85%–95% 的确定性区间；不得改用新随机规则 |
| 预警证据 | 从修饰前的 decoration 取确认记录，不从限幅后的图表数据重算 |
| 决策持久化 | 沿用现有台账及四键，不新建一份路径专用决策账，不覆盖旧人工记录 |

规格加入或改变后，须使相关缓存、当前提交结果及发布策略失效，重算窗口内新路径结果；不能只补画一条规格线。

## 8. 接入位置、快照与刷新

### 8.1 职责分工

| 层/位置 | 建议职责 |
|---|---|
| `indicator_domain/infrastructure/qtime/` | 只读有界履历与产品主数据访问、schema 到标准字段映射、来源健康、与原仓储输出接合 |
| `indicator_domain/core/qtime/` | 继续复用当前修饰规则，本需求不要求新增通用站点关联引擎 |
| `indicator_domain/application/qtime/` | 接收相同标准数据，继续使用现有监控、缓存和健康传播接口，不增加路径专属业务流程 |
| `indicator_domain/composition.py` | 装配必要的固定路径补充来源，不在页面创建另一套数据库对象 |
| `app/sections/indicator_domain/qtime/` | 延续既有筛选、查询和产品分图流程；通过仓储返回的站点选项识别新路径 |
| `app/charts/indicator_domain/qtime/` | 原图表直接消费标准明细，不新增路径专属公式、修饰或展示规则 |

这是接入职责说明，不声称新的适配器已经实现。实现应优先收敛在取数侧，不为本需求新增通用配置体系。

### 8.2 快照与一致性要求

1. 按 [ADR-0023](../ADR/0023-qtime-local-source-snapshot-and-decoration-boundary.md) 保持厂别级统一源事实快照。补充路径应并入该厂别事实，不按产品/路径制造第二套同义 L1。
2. 继续遵循现有源快照与修饰结果的分离边界。若接入需要更新源版本或签名，按现有机制失效，不能把旧快照当作已包含新路径。
3. 取数侧须向 `list_step_options()` 提供新路径选项，不能继续只依赖原成品表的路径集合；无需改造页面筛选方式。
4. 产品与路径筛选继续在厂别级事实之上进行，满足启用产品边界，保留三列产品图布局及查询门控、fragment 隔离和滚动行为。
5. 把新增源接入已有的正常刷新、全量刷新和后台生产入口；沿用既有刷新/发布流程，仅补足新来源实际需要的读取范围，不再新建调度或业务处理链路。
6. 对同一厂别合并结果，任何必要来源失败都不能发布为完整新鲜结果。保留最后成功快照并传递降级状态，不用部分新结果覆盖完整旧结果；不把数据失败当作零事件。
7. 使用现有缓存签名和失效机制反映新增源及产品映射输入；不引入新路径专用的规格状态协议。后续规格变更仍走现有规格与刷新机制。
8. 若原数据源以后也出现同一路径，必须约定每个路径只有一个生效事实来源，避免两份结果并列计数；默认不静默合并不同时间口径的数据。
9. 正式预警继续由正常生产流程发布，共用读取器不因缓存 miss、缺行或无规格而查询履历。功能异常详细信息写日志，维持本页已约定的不显示功能异常提示条的行为。

## 9. 验收标准

| 编号 | 场景 | 验收结果 |
|---|---|---|
| AC-01 | 已有成品源中无新路径 | 启用后可选择 `1A200 → 21100`，补充来源独立构造，不要求先有 Q-Time 主记录 |
| AC-02 | 同 Lot 两次进站分别 08:00、10:30 | 得到 2.5 小时；未混入 TrackOut 或主表 ENTER_TIME |
| AC-03 | 原始站点包含字母 | `1A200`、`21100` 精确保留并正确进入 `f_step/t_step` |
| AC-04 | 事件规格映射到 M626 | 输出 `prodcode=M626`，按该产品筛选；不会因重复主数据把一对事件扩成多行 |
| AC-05 | 同规格存在多个有效产品代码或字段无法映射 | 不任意归属；记录歧义/缺口，不作为完整成功结果发布 |
| AC-06 | 同一起点关联到多条终点记录 | 取数去重以 CPT 生效的分组、目标时间排序及 `RN=1` 为基线；不额外加入返工分段或终点不复用规则 |
| AC-07 | 缺少时间或存在取数歧义 | 不用 0、当前时间或其他批次伪造标准数据；在取数侧记录并说明问题，不自行改写后续业务规则 |
| AC-08 | 较早起点在原增量重叠段之前，后来取得终点 | 在完整滚动源窗口重新补取该路径，更新早期起点的记录而不重复叠加；不输出窗口外起点 |
| AC-09 | 两端厂别不同 | 按分别核实的源厂别配对，不因报表归类 ARRAY 错误过滤目标厂别 |
| AC-10 | 当天截止、日期前推、日期排除及微秒边界 | 与当前输出政策一致，原始时差与源快照不被平移或修饰污染 |
| AC-11 | 规格未提供 | 不杜撰规格；空规格输入继续走原服务与原图表，不新增预警旁路、分母规则或状态文案 |
| AC-12 | 后续测试规格及三态决策 | 在临时测试数据下与既有 `True/False/Delete`、展示限幅及真实预警证据完全一致 |
| AC-13 | 重复四键或同秒多个不同事件 | 接入修饰前识别冲突，不在正式查询时发生不可解释的合并错误 |
| AC-14 | 缓存命中和全量/增量刷新 | 新来源正确接入已有机制；不因新增路径重新设计缓存、刷新或发布流程 |
| AC-15 | 新来源读取失败 | 保留旧成功结果并传递降级；日志可定位来源及阶段，不发布部分结果为 fresh |
| AC-16 | 原路径回归 | 原来源、口径、人工台账、图表、预警和单腔模块均未被新增路径规则覆盖 |

建议实施验证以新增取数 SQL/适配和标准字段契约为重点，再对原服务、修饰及页面做回归；最后在元数据和规模核验后执行有界真实样本验证。临时 Excel/Parquet 或测试服务按项目隔离与清理要求处理。

## 10. 实施阶段与待核验项

### 阶段 A：来源可用性核验

确认实际履历对象、时间/事件键、两端工厂、产品规格字段、主数据版本，以及同 Lot 跨站可关联性；输出有限样本与覆盖结论。未通过时明确缺失字段或权限，不宣称端到端可用。

### 阶段 B：无规格的数据接入

确定源时间字段、查询范围和 CPT 去重方式的字段对应关系，补充固定路径数据并输出标准明细。数据随即交给原有报表逻辑，不开发独立返工、统计、预警或展示流程。无需等待具体规格数值即可核验取数契约。

### 阶段 C：用户提供规格后

按现有规格来源与准备入口加入正式规格，执行现有刷新和监控流程，回归既有修饰、人工决策与预警发布行为；不在此阶段另外设计一套下游算法。

实施前尚需固定的事项：

| 事项 | 当前状态 |
|---|---|
| 两站均取 TrackIn、以小时计差 | 用户已确认 |
| 产品主数据及关联条件 | 用户已提供；事件侧实际字段及有效版本尚未核验 |
| 规格数值、产品差异及生效范围 | 用户稍后提供；不阻止阶段 B |
| 两端真实厂别及 Lot 连续性 | 待元数据/有界样本核验 |
| 起点作为显示锚点 | 已通过真实样本确认，保持 CPT 起点分组和原人工决策键唯一性 |
| 取数关联与去重 | 参考 CPT 生效逻辑；不增加新的返工分段或终点不复用规则 |
| 回看长度、查询容量与超时 | 待规模和样本评估确定，不以未知规格猜测 |

## 11. 本次已做的验证与局限

已解析 CPT 的生效 `SEARCH` 数据集，并核对当前站点仓储、监控服务、修饰、图表、产品映射模式及相关 ADR；没有把备份注释 SQL 当作生效逻辑。
