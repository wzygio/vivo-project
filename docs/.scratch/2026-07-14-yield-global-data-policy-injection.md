# 集中 Yield 通用数据策略并在底层一次注入

Category: `enhancement`  
Status: `ready-for-agent`  
Created: `2026-07-14`  
Source: 用户关于 `target_defect_groups`、`work_order_types` 全局化及 Yield 配置单点注入的需求  
Related: `CONTEXT.md`、Yield Domain 设计参考、配置加载与快照回退测试

## Design assessment

设计方向合理，但需明确“底层修改数据”的边界：

- `target_defect_groups` 与 `work_order_types` 在全部已启用产品中取值一致，属于应用级数据策略，应由全局配置维护，产品配置只保留产品差异。
- 配置文件应在应用组合根加载并校验；Yield 数据边界接收一个已校验的数据策略对象。上层服务、告警与页面不应再次读取这两个字段并重复过滤。
- Parquet 快照应保留从数据源取得的、尚未按 Defect Group 做不可逆抹除的数据；Repository 在返回 DataFrame 前统一应用一次 Defect Group 策略，使数据库新查、快照命中、增量合并和容灾回退具有相同结果。
- Work Order Type 是查询约束，必须在数据库边界应用。其策略版本必须参与缓存/快照隔离，避免全局配置变化后继续命中旧口径快照。
- 本次只集中并下沉这两项通用数据策略；产品专属的 defect multiplier、人工覆盖、警戒线、热点脚本等仍由各自负责的处理阶段消费。

## Current context

- 五个产品配置重复声明完全相同的 `target_defect_groups` 与 `work_order_types`。
- 配置加载器已经按 `global < product` 深度合并，因此全局 `data_source` 默认值可以与产品 `product_code` 自然组成完整配置。
- Yield 查询 DTO 同时携带动态查询条件和静态数据策略；页面、应用服务、DAO、Repository、告警服务和展示层均直接或间接消费相同字段。
- 数据库新查路径会在 DAO 抹除非目标 Defect Group，快照命中路径又在 Repository 重复抹除；这使快照可能持久化不可逆的、依赖当时配置的结果。
- Session 配置热重载目前只观察产品 YAML；配置移入全局 YAML 后，修改全局策略不会触发会话配置刷新。
- 未发现与本需求冲突的 adr。Yield 核心良率散布、Mapping 级联衰减、数据库单例和 Streamlit 页面缓存均为既有红线，不在本次改动范围。

## Desired outcome

全局配置成为两项 Yield 数据策略的唯一配置来源。配置在边界被转换为明确、可校验、可参与缓存签名的数据策略，并一次注入底层数据提供者。数据提供者对所有来源路径统一应用策略后把一致的数据交给上层；上层不再按同一配置重复过滤。

## Key interfaces

- `AppConfig.data_source`：继续向调用方暴露合并且校验后的 `product_code`、`work_order_types`、`target_defect_groups`，但后两者来自全局配置。
- `YieldQueryConfig`：只描述一次请求的动态条件（产品和时间范围），不再混入静态数据策略。
- Yield 数据策略值对象：封装 Work Order Type 与目标 Defect Group，提供稳定签名，并作为 Repository 的构造依赖。
- `PanelRepository.get_panel_details()`：无论数据来自新查询、有效快照、增量合并或降级快照，均只在返回前应用一次目标 Defect Group 修饰；持久化快照不保存该不可逆修饰结果。
- Yield 快照刷新入口：接收已加载的应用配置，在同一个边界构造动态查询和数据策略，不要求页面重新拆读两个配置字段。
- 告警与页面：使用底层已经限定的数据，不再按 `target_defect_groups` 二次筛选。

## Acceptance criteria

- [x] `target_defect_groups` 与 `work_order_types` 只在全局 YAML 声明一次，所有启用产品加载后仍得到当前相同的有效值。
- [x] 产品 YAML 不再重复声明这两个通用字段，产品 `product_code` 及其他专属配置保持不变。
- [x] 修改全局 YAML 会参与 Session 配置热重载判断。
- [x] Yield 动态查询契约不再携带静态数据策略；页面不再为了刷新快照而读取这两个配置字段。
- [x] Work Order Type 只在底层数据库查询边界作为查询约束使用，并参与快照隔离/签名。
- [x] 新查、快照命中、增量合并和降级返回都通过 Repository 的同一公开行为得到一致的 Defect Group 修饰结果。
- [x] 非目标 Defect Group 的 defect code/description/group 在返回上层前被置空，但原始快照写入前不做该不可逆抹除。
- [x] 告警服务和主看板不再依据 `target_defect_groups` 重复过滤；它们基于数据提供者的输出工作。
- [x] 不修改已验证的 Sheet/Lot 散布算法、Mapping 级联衰减算法、数据库连接单例、Streamlit 缓存装饰器及快照增量/容灾语义。
- [x] 相关单元测试、配置集成测试通过；全量 `uv run pytest tests/ -v --tb=short` 通过，或明确记录与本改动无关的既有环境阻塞。

## Behaviors to test (TDD order)

1. 任一产品通过公开配置加载接口继承全局 Yield 数据策略，产品文件无需重复字段。
2. Session 热重载观察全局配置与当前产品配置的组合版本。
3. Repository 对数据库新查结果应用一次策略，同时写入未做 Defect Group 抹除的快照。
4. Repository 对快照命中结果应用同一策略，结果与新查路径一致。
5. Work Order 策略变化产生不同的快照身份，避免旧口径复用。
6. 告警与刷新入口只消费已注入策略/已限定数据，不再自行读取并二次过滤通用字段。

- 清理、迁移或删除已有 Parquet 快照；新策略可通过新的快照身份自然重建。
- 将所有产品专属 processing/path 配置全局化。
- 顺带修复 SQL 参数化、数据库连接、页面视觉或其他领域配置问题。

## Agent Brief

**Category:** enhancement  
**Summary:** 将 Yield 的通用数据策略集中到全局配置，并以单一、可签名的策略对象注入数据提供者，使所有数据来源在进入上层前获得一致修饰。

**Current behavior:**  
相同策略在每个产品配置中重复维护。动态查询 DTO 混入静态策略，多层调用方反复读取字段；新查与快照路径分别清洗 Defect Group，可能把依赖配置的不可逆结果写入快照并造成口径漂移。全局配置变化也不会触发当前 Session 热重载。

**Desired behavior:**  
全局配置是策略的唯一来源。配置边界构造一次数据策略并注入 Repository；Repository 保存原始查询/合并结果，在返回上层前统一应用 Defect Group 修饰。Work Order 策略约束数据库查询并参与快照身份。上层只消费已限定数据。

**Key interfaces:**

- `AppConfig.data_source` — 提供合并校验后的产品代码和全局数据策略。
- `YieldQueryConfig` — 仅保留动态查询条件。
- Yield 数据策略值对象 — 不可变地表达 Work Order 与 Defect Group，具有稳定缓存签名。
- `PanelRepository` — 构造时接收数据策略，对所有返回路径提供一致行为。
- Session 配置版本 — 同时感知全局与当前产品配置。
