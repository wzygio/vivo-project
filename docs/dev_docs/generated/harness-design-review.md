# 项目 Harness 设计评估与修订记录

核验日期：2026-09-12。范围：根目录 `AGENTS.md`、`ARCHITECTURE.md`、`CONTEXT.md`、`HARNESS.md`，以及维护这四者所需的知识路由修复。本文以用户的四文件设计、当前仓库和公开一手资料为依据；按用户后续要求，不采用 `manage-harness` 或其全局模板作为验收标准。

## 1. 结论

**四文件设计合理，适合当前个人开发项目。需要优化的是职责与加载条件，而不是增加更多文件或平台。**

`AGENTS.md` 应是 Agent 的入口指令和地图，承载关键约束及“什么问题读什么”；若把它定位成完整的“项目架构与规范”，就会与另外三份文档重复。`CONTEXT.md` 的重要规范应限定为项目背景和业务约束，代码依赖规则由 `ARCHITECTURE.md` 持有，知识维护规则由 `HARNESS.md` 持有。

四份 Markdown 是 Harness 的文档接口。完整的工作环境还包括工具、测试、执行权限和反馈证据；这不意味着当前必须再建设一套 Harness 平台。现有测试、命令和文件路由可以继续承担这些职责。

这种“小入口、按需读深入资料”的方向与 OpenAI 的仓库实践一致：其工程文章把 AGENTS.md 用作地图，并将深入知识、计划和验证资料保存在仓库内。文章中的规模和自动化程度是特定团队的实践，不是本项目必须照搬的规范。[OpenAI：Harness engineering](https://openai.com/index/harness-engineering/)

## 2. 建议的职责划分

| 文件 | 回答的问题 | 加载条件 | 避免收录 |
|---|---|---|---|
| `AGENTS.md` | 我必须遵守什么？下一步去哪里找？ | 仓库入口；由实际 Agent 工具或显式读取提供 | 全部架构、算法、长篇工作流程 |
| `CONTEXT.md` | 项目服务谁？如何运行？哪些业务约束不能误改？ | 首次实质任务及业务约束相关修改 | 重复的三级代码树、全部 Harness 产物目录 |
| `ARCHITECTURE.md` | 功能归谁？依赖怎样走？在哪层哪个子模块修改？ | 代码定位、运行流和依赖边界相关任务 | 每个程序的介绍、任务进度 |
| `HARNESS.md` | 知识如何组织、读取、更新和验证？ | 修改指令、知识路由、文档所有权时 | 第二份业务规范或应用架构说明 |

`AGENTS.md` 是公开约定的 Agent 指令入口；其他三个文件名是本项目约定，不能假定所有工具都会自动读取。必须在入口写明触发条件并提供路径。[AGENTS.md 官方说明](https://agents.md/)

例如，修改 Q-Time 超规逻辑时，路径应为 `AGENTS → CONTEXT 的相关约束 → ARCHITECTURE 的 indicator/qtime → 相关源码、契约和测试`；无需读 HARNESS 全文。调整知识命名和文档路由时，才进入 `HARNESS → references/index`。修改页面导出则必须触发普通模式展示边界，不能只搜导出函数而漏掉业务限制。

## 3. 高优先级：当前影响 AI 开发的实际问题

| 问题与原有证据 | 可能后果 | 本次修正 |
|---|---|---|
| AGENTS 将 CONTEXT 描述为快速了解架构，将 HARNESS 描述为快速了解项目信息，路由目的混淆 | Agent 找错资料，重复读取，或跳过约束 | 改为任务触发表；明确首次项目理解、代码定位、展示修改、Harness 修改的去向 |
| CONTEXT 中两个不同目录表都叫 Harness Architecture；CONTEXT/HARNESS 重复列文档产物 | 同一内容发生漂移，Agent 不知道哪份权威 | CONTEXT 保留项目与运行资源入口；HARNESS 集中维护知识与工作产物生命周期 |
| `.planning/` 被称为 `.scratch/` 的高级版，而实际 `.scratch/` 已拥有 PRD/issue 约定 | 同一需求被复制两份，更新与完成状态不一致 | 明确 PRD/issue 与执行计划互补，用同一任务标识关联，简单任务不强制创建两套文件 |
| 已删除 retrospective，但知识路由仍链接它；矩阵定时专题链接也实际不存在 | Agent 反复找文件或凭空推断不存在的文档内容 | retrospective 路由改至 HARNESS；缺失专题明确标注，并转到已核验运行入口，未恢复用户删除的文件 |
| ARCHITECTURE 的矩阵说明插入表格中间，导致 `tests/` 行脱离表格；四文件混用中英文和含义不清的标题 | 人和 Agent 都难以稳定提取结构；翻译时还可能丢失规则 | 修复表格、统一四文件为英文、保留现有三级目录与代码标识，不翻译或重命名真实资源 |
| 用户新增的普通模式边界较长，若只笼统链接 CONTEXT 容易漏读 | 页面正常分支合规，空状态、列菜单或导出却泄露内部信息 | AGENTS 和 ARCHITECTURE 增加明确的 UI/导出触发路由；详细规则只保留在 CONTEXT |

以上是已存在的导航或表达问题，不是要求补齐大型企业平台。修订保留了日期前推、最新报表日截止、数据库生命周期、缓存、快照回退和普通模式展示边界，未借整理文档修改业务行为。

特别澄清：`admin=true` 是当前展示模式约定，不应在英文中表述为已经具备身份认证和授权。文档现已区分这两个概念，同时保留用户要求的普通模式信息边界；本次不进行权限改造。

## 4. 低优先级：出现明确需要后再引入

下表是结合本项目作出的工程判断，不是“业内合规清单”。

| 可选能力 | 什么时候值得引入 | 最小实施方式 | 当前不必建设的部分 |
|---|---|---|---|
| 文档链接与路由自动检查 | 断链/目录迁移错误反复出现，人工核对开始占用时间 | 一个本地脚本检查链接、目录和关键文档语言；之后再接现有 CI | 独立文档治理服务 |
| 小规模 Agent 任务评估 | 更换模型、规则或工具后经常误定位、漏约束或重读全部文档 | 固定几类真实任务：找 Q-Time 仓储、改普通模式导出、定位矩阵调度；记录路径准确性、漏项和重试 | 排行榜、复杂评分平台或未经测量的 token/覆盖率硬门槛 |
| 长任务交接记录 | 经常跨会话开发，需要重新发现已完成事项 | 复用 `.planning/` 记录当前状态、下一步、失败原因和证据，链接 PRD/issue | 常驻多 Agent 调度器、另建一套任务数据库 |
| 更可重复的隔离验证环境 | 资源文件、日期或真实数据库使回归无法稳定复现 | 先固定离线 fixture、环境前提和明确的验证命令 | 立即引入 Kubernetes、复杂发布平台或全部容器化 |
| 更强的机器可执行边界 | 同类跨层 import 或缓存错误反复发生 | 逐步扩展现有 `tests/architecture/` 和行为回归；检查输出给出修正入口 | 将全部文档规则都变成阻断 hook |
| 子目录 AGENTS 或代码索引 | 领域明显扩大，且局部约束确实不同；文本搜索持续低效 | 在真实差异处增加局部指令，或由用户决定启用索引；公共规则仍只维护一处 | 为每个目录复制 AGENTS，自动建立未经授权的索引 |
| 文档保鲜与证据清单 | 生成报告、设计方案和正式决策数量增加，出现误用过时结论 | 给评估注明日期/范围，明确 proposed 与 accepted；定期人工抽查关键路由 | 自动把所有聊天或生成内容提升为项目规则 |

渐进式披露的价值在于按任务提供必要、相关的上下文，并保留动态检索能力，而不是追求固定行数或把所有资料都塞进初始提示。[Anthropic：Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

对于跨上下文窗口的长任务，Anthropic 的实践强调可恢复的进度记录、可执行验证和清晰交接。因此当前优先复用已有文件计划即可，不必直接采用多 Agent 架构。[Anthropic：Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

## 5. 逐文件修订结果

- [AGENTS.md](../../../AGENTS.md)：简洁入口、按任务读取、关键安全边界、ECC 路由、文档更新归属。保留 CodeGraph 有索引时优先、无索引时不自行建索引的规则。
- [CONTEXT.md](../../../CONTEXT.md)：项目目的、运行假设、重要路径与业务约束。普通模式规则已完整翻译，包括先剔除不应下发的内部数据、异常安全提示及导出检查。
- [ARCHITECTURE.md](../../../ARCHITECTURE.md)：完整翻译并保留 domain/layer/submodule 结构、职责表、依赖方向、查找示例与关键技术契约。保留已存在的 app 层矩阵调度/快照边界，未将现状“美化”为纯后端实现。
- [HARNESS.md](../../../HARNESS.md)：明确四文件的 owner、按需加载、产物生命周期、单一权威来源、最小验证以及演进记录。现有 `.scratch/` 和 `.planning/` 不迁移。
- [references/index.md](../../../references/index.md)：修复退休文件、缺失矩阵专题及缺失共享内核概览的三条路由；缺失专题转向已核验的架构/代码入口，未虚构正文。保留业务知识正文、命名约定和 file-level 路由例外。英文统一范围为用户指定的四份根文档，不扩展为全仓翻译。

本次未修改全局技能/模板、未安装工具或 hooks、未增加 Agent 编排、未改业务代码、未恢复 `references/retrospective.md`，也未将生成报告作为新的强制政策。当前用户请求优先于此前的维护技能建议。

## 6. 验证与阅读方式

已检查四文件英文正文、本地链接/锚点、三级目录与磁盘的一致性、关键约束保留和 diff 空白格式：四文件无中文残留，六份修改/新增文档中的 72 处本地链接及相应锚点有效，51 个架构目录全部存在且前三层无遗漏。仅文档与路由变化，无须以业务测试通过来证明文档正确；本次未运行业务回归、浏览器或性能测试。

日常使用只需让 Agent 从 AGENTS 按任务走下去。发现某次开发漏读规则时，先修复对应的触发描述或路由；只有重复出现且人工维护明显吃力，再引入上表中的自动化。
