# 个人开发者如何理解本项目的测试缺口与最小发布检查

日期：2026-09-09。本文解释[后端架构评估中的 H5](backend-ddd-architecture-assessment.md#h5建立可重复的最小发布与检查流程)，结合仓库现有测试说明哪些保障已有、哪些需要补齐，以及缺失可能造成什么后果。

**你的项目已经有相当多的测试，也已经有具备“验收”作用的测试。当前最需要的是补齐数据失败等关键场景，并明确每次发布必须运行哪些检查；无需为了个人项目建立测试部门、审批流程或大型 CI/CD 平台。**

本轮按你的决定实施 H1、H4；H5 仅提供解释和建议，不新增发布脚本或流水线。H2 的版本冲突、审计与快照原子发布增强，以及 H3 的权限改造均暂缓，不作为这次交付的前置要求。

## 1. “验收测试”到底验收什么，为什么一个人也用得上

验收是判断：**给定业务条件，系统是否产生你愿意交付给使用者的结果。** 你既是开发者，也可以是验收者；不需要另一个同事签字。

例如，“数据库故障时允许看旧报表，但必须提示数据已经过期，不能显示当前一切正常”，就是验收标准。它可以变成 pytest 自动测试，也可以通过浏览器操作检查。是否叫 `acceptance/`、是否使用专门框架，都不是关键。

“单元、集成、端到端”主要描述测试跨越多少组件；“验收”描述测试要证明的业务承诺。它们不是互斥的四个目录。

| 形式 | 本项目可以验证什么 | 无法单独证明什么 |
|---|---|---|
| 单元测试 | 给定测量值与规格，超规判定正确；失败状态正确映射为未知 | 实际 SQL 能执行、页面接收并展示该状态 |
| 应用用例测试 | 注入 fake 数据源，调用真实服务，核对报表和健康状态 | 真实数据库权限、驱动与网络正常 |
| 离线集成测试 | 多个真实组件连接起来；临时工作簿读写；SQLite 执行 SQL 契约 | 生产数据库方言完全兼容、真实共享目录权限正常 |
| 浏览器测试 | 查询按钮、筛选、缓存后二次查询和提示文案确实可见 | 所有算法组合都正确、生产数据源一定可用 |
| 发布环境检查 | 干净环境能安装、启动，必要资源齐全 | 所有业务行为都正确 |

同一条“旧数据不得显示当前正常”的验收标准，值得分别在服务层验证状态、在页面层验证展示。无须把所有底层边界情况都重复做成浏览器测试。

## 2. 仓库已经具备哪些保障

以下结论来自测试内容，不依赖文件夹名称，也不代表这些测试本次都已运行通过。

| 现有证据 | 已经保护的行为 | 仍需关注的边界 |
|---|---|---|
| [Yield 数据策略测试](../../../../tests/unit/test_yield_repository_data_policy.py) | 工单策略参与快照身份；源缺陷先持久化，再按策略处理；日期前推 | 原评估时未覆盖“跨月部分读取失败，却发布完整结果”的行为 |
| [Q-Time 仓储测试](../../../../tests/unit/indicator_domain/infrastructure/qtime/test_repository.py) | 查询参数绑定、源时间快照、过期刷新、断库回退、安全错误 | 原有回退测试主要断言旧数据仍能返回，没有证明普通查询页面一定告知降级 |
| [Sheet OOS 刷新集成测试](../../../../tests/integration/test_sheet_oos_refresh_integration.py) | 使用临时真实工作簿验证决策同步、刷新、写失败保留旧状态 | 它是离线文件链路验证，不能证明真实用户机器的 Excel/文件权限条件 |
| [预警矩阵集成测试](../../../../tests/integration/test_alert_matrix_integration.py) | 多产品、多域状态汇总与单域判据一致；查询期间工作簿不被改写 | 原评估时缺少健康状态断言；本轮已在[矩阵服务测试](../../../../tests/unit/app/sections/monitor/test_alert_matrix_service.py)补充“未知与正常不可混淆”的回归 |
| [Q-Time SQL 集成测试](../../../../tests/integration/indicator_domain/test_qtime_repository_sql.py) | SQLite 内存数据库实际执行 SQL，验证时间、厂别、产品和站点筛选及规格关联 | SQLite 不是部署使用的真实数据库，不覆盖其全部方言、权限与性能 |
| [Q-Time 浏览器脚本](../../../../tests/e2e/qtime_report.js)与[隔离应用](../../../../tests/e2e/fixtures/qtime_app.py) | 查询交互、图表、重复查询、安全失败文案 | 原有失败场景不等于已经覆盖“有旧快照且没有超规记录”的展示 |
| [Core 架构测试](../../../../tests/architecture/test_decoration_boundaries.py) | 阻止 Core 混入部分 Excel 持久化依赖和调用 | 原评估时没有完整保护已迁移 application 的出站依赖；本轮 H4 补齐相关约束 |

所以，不能说你“没有验收测试”。Sheet OOS 的决策变更结果、预警矩阵的一致性与只读行为，已经具有明确的业务验收价值。缺口在具体场景、组件之间的连接，以及发布时是否稳定执行这些测试。

## 3. 具体示例一：跨月查询部分失败，数字看起来却完全正常

假设查询 7 月和 8 月良率。为便于解释，采用最简单的“良品数 ÷ 总数”统计，不涉及项目其他修饰规则：

| 月份 | 总数 | 良品数 | 单月良率 |
|---|---:|---:|---:|
| 7 月 | 1,000 | 990 | 99% |
| 8 月 | 1,000 | 900 | 90% |
| 完整两月 | 2,000 | 1,890 | 94.5% |

如果 8 月 SQL 超时，加载器把异常转换为空表，仓储再跳过空表，只拼接 7 月数据，统计公式仍能正确算出 99%。页面也可能正常显示图表。然而使用者选择的是两个月，看到的却只有一个月。

这里公式没有算错，错误在于**不完整数据被当成完整查询结果**。如果再将它保存成“新快照”，后续命中快照的用户也会继续看到这个不完整窗口。这是原评估指出的控制流风险，示例数字是假设，不是实际生产事故记录。

为什么现有正常路径单测可能全部通过？因为测试给公式提供完整 DataFrame，或者把数据库固定替换成“总能成功”的 fake，没有制造第二个分片失败；测试从未询问“窗口完整吗”。

### 最小验收场景

| 输入/前置条件 | 动作 | 必须满足的结果 |
|---|---|---|
| 两个月均成功 | 查询两月窗口 | 返回完整数据，健康状态表示本次可用 |
| 第一个月成功，第二个月抛出读取错误，没有旧快照 | 查询同一窗口 | 明确失败或不可用；不得把第一月单独发布为完整新快照 |
| 相同故障，但存在旧快照 | 查询同一窗口 | 如允许回退，返回旧数据并标记降级；覆盖窗口不足时不能声称完整 |
| 两个月成功执行 SQL，其中一个月合法无记录 | 查询同一窗口 | 这是成功查询的空分片，不应被误判为故障 |
| 全部成功但均无记录 | 查询空业务窗口 | 能区分“查询成功无记录”和“数据读取失败” |

最便宜的实现方式是：fake 数据源按月份返回固定 DataFrame 或抛出类型化异常；快照放在 `tmp_path`；调用真实仓储；检查返回状态与快照内容。无需关闭生产数据库，也无需等待真实网络超时。

测试中的预期值应手工给定，不要再调用同一个生产函数算“正确答案”。涉及日期前推时显式固定策略和时间，避免测试受个人配置或月份变化影响。仓库现有 Yield 数据策略测试已经展示了这种做法。

## 4. 具体示例二：旧 Q-Time 数据没有超规，不代表现在正常

假设昨天的快照没有任何超规记录，今天数据库不可用。系统回退到昨天快照后，原有规则依然能算出“0 条超规”。这个结果只能说明旧数据里没有超规，不能证明今天正常。

最容易漏掉的是中间一段：仓储知道自己用了旧快照，但服务只传出 DataFrame，缓存 payload 和预警矩阵再也拿不到降级信息。页面不会崩溃，截图也可能很漂亮，但绿色“正常”会误导使用者。

因此本轮 H1 的验收应从仓储延伸到使用者：

| 输入/前置条件 | 动作 | 预期 |
|---|---|---|
| 过期快照中无超规；数据库报错 | 普通查询 | 显示旧数据/降级提示；有元数据时提供覆盖窗口、最近成功时间 |
| 同上 | 再次点击查询，命中应用缓存 | 降级提示仍在，不能因缓存只保留数据而消失 |
| 同上 | 查看预警矩阵 | 当前健康判断为未知或不可用，不能仅因超规数为零显示当前正常 |
| 无快照；数据库报错 | 普通查询 | 安全错误文案，不展示伪造的正常结果 |
| 数据库成功且确实无记录 | 普通查询 | 展示无数据，与读取故障明确区分 |

服务层用 fake 覆盖全部状态组合；页面只选择“旧快照零超规”和“完全不可用”等少量关键场景。浏览器验证重点是提示可见、二次查询提示仍在、预警状态不误报正常。内部状态测试通过，仍不能替代实际页面验证。

## 5. H4 的架构检查为什么也算必要测试

假设为方便临时修改，某个已迁移的 application 服务又直接导入具体 Excel 仓储。当前业务测试可能仍通过，因为这台电脑刚好拥有全部依赖。但下次想给服务注入内存数据源，仍会触发真实基础设施导入；更换持久化实现也可能再次修改业务编排。

H4 要保护的是一条可自动执行的约定：已迁移服务通过消费方端口使用出站能力，具体适配器由组合根装配。

两类证据相互补充：

1. 应用服务测试：传入内存 fake，能完成关键用例，验证依赖确实可以替换。
2. 架构测试：扫描导入，禁止已迁移区域重新依赖具体基础设施；存量例外有明确范围。

这类检查成本通常很低，个人开发同样受益：它替几个月后的自己记住架构约定。它不证明 SQL 或业务算法正确，也不是要求每个函数都增加一个接口。本轮 H4 完成的边界应以实际架构测试为准，不把渐进迁移写成全仓“完全纯净”。

## 6. H5 的另一个缺口：装得起来与测得正确是两件事

[pyproject.toml](../../../../pyproject.toml)已经配置依赖，仓库也有 [uv.lock](../../../../uv.lock) 和 [requirements_locked.txt](../../../../requirements_locked.txt)。问题不是“没有锁文件”。

两个内部包来自相邻目录 `../packages/common_utils` 和 `../packages/file_decryption`，且为 editable 安装。只复制 `vivo-project` 到新电脑，可能缺少这两个目录；即使目录存在，里面的未固定源码变化也可能改变应用行为。第三方依赖锁定不能自动保存这些本地源码的每一次变化。

例如，所有单测在旧电脑通过；换机后启动报内部包不存在。这不是少写一个良率单测能解决的问题，需要交付清单记录内部包版本和获取方式，再做一次干净环境安装检查。

适合当前规模的选择是：继续使用 uv，但交付版本明确的配套内部包源码，或者以后使用固定版本 wheel。先选定一种实际可用的方法，无需同时建设私有包仓库、容器平台和自动部署系统。

在独立验证目录及新环境中，可以用 `uv sync --locked` 检查锁文件与项目声明一致并安装依赖；它不会替你补齐未交付的本地目录。uv 官方说明了锁定与同步行为：[Locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/)。**本文没有执行干净环境安装，也没有修改当前虚拟环境。**

## 7. 现在如何执行一套足够小的本地发布检查

### 7.1 已有 smoke 的真实范围

[tools/smoke.py](../../../../tools/smoke.py)支持 `spc`、`equipment`、`yield`、`all`；默认与 `all` 都运行 `tests/unit`。它会保留 pytest 退出码，这一点已经正确。

但 `all` 不包含 `tests/architecture`、`tests/integration` 或 JavaScript 浏览器脚本。因此不能从“smoke all 成功”推断“架构、SQL 集成、浏览器都通过”。这就是 H5 提出统一最小入口的直接原因之一。

### 7.2 不改脚本也可以先运行的检查组合

下面从仓库根目录使用已经安装好的 `.venv` 运行。独立命令用于清晰展示范围；执行失败应处理原因后再发布，不应只看最后一个命令的成功状态。

```powershell
# Python 单测与架构约束；结果目录只用于本次测试产物
.venv/Scripts/python.exe -m pytest -q tests/unit tests/architecture `
  --basetemp=output/test-results/release-unit-architecture

# 已确认采用内存数据库或临时文件的选定离线集成链路
.venv/Scripts/python.exe -m pytest -q `
  tests/integration/indicator_domain/test_qtime_repository_sql.py `
  tests/integration/test_sheet_oos_refresh_integration.py `
  tests/integration/test_alert_matrix_integration.py `
  --basetemp=output/test-results/release-offline-integration
```

`--basetemp` 目录应专用于测试，不放需要保留的用户文件。pytest 提供 `tmp_path` 与 `monkeypatch`，分别用于隔离文件和临时替换依赖；这些能力已被项目使用：[pytest 内置 fixtures](https://docs.pytest.org/en/stable/builtin.html)。

这是**建议的本地检查组合，不是本文件声明已经执行通过的测试记录**。全量 unit 仍可能依赖仓库资源或现有配置；首次把它定为固定检查时，应确认运行稳定并记录环境前提，不能仅凭 `unit` 目录名认定完全自包含。

不建议把整个 `tests/integration` 无差别加入“离线”命令。[Equipment 数据库测试](../../../../tests/integration/test_equipment_parts_db.py)会创建真实 `DatabaseManager` 并读取实际资源，有些分支在结果为空时执行 `pytest.skip`。因此运行结束没有失败，仍不等于数据库连通且查到了预期业务数据；发布记录必须区分通过、跳过和未执行。

### 7.3 按改动选择补充检查

| 改动 | 最小补充检查 | 主要防止的后果 |
|---|---|---|
| 只改核心公式 | 受影响规则测试、边界值和手工算出的预期值 | 公式在零分母、边界规格等情况下出错 |
| 改仓储、缓存或失败处理 | 分片故障、旧快照回退、合法空结果、应用状态传递 | 数据缺失或过期被当成正常 |
| 改端口与组合根 | 应用 fake 测试、具体适配器契约、架构测试 | 假接口与真实装配不一致、依赖反向渗透 |
| 改查询页面或提示 | 隔离 fixture 下浏览器查询与重复查询 | payload 正确但提示未显示、缓存后提示丢失 |
| 改 SQL、驱动或数据库配置 | 离线 SQL 契约，再在明确的验证环境执行只读真实连接检查 | SQLite 测试通过，真实方言或权限失败 |
| 改依赖、内部包或部署方式 | 新环境固定版本安装、启动关键页面 | 旧环境隐藏缺失依赖，新机器无法运行 |

现有 `tests/e2e/qtime_report.js` 是接收 `page` 的函数脚本，并非直接由 pytest 收集。使用仓库现有浏览器执行方式运行，并启动对应 fixture；不要把 `pytest tests` 当成已执行它。若只做人工检查，记录页面、输入、实际结果即可，截图与日志放在 `output/test-results/` 或 `output/tmp/`。

### 7.4 个人发布记录可以很短

每次真正替换运行版本时，记录以下内容即可，不需要多人签批：

- 代码提交或明确的工作区版本，以及两个内部包的实际版本。
- 安装环境、锁文件版本和必需配置的来源；不记录密钥值。
- 执行的检查命令、退出码、通过/失败/跳过情况；未做真实数据库或浏览器检查就直接写未执行。
- 本次修改影响的关键业务场景及观察结果。
- 使用哪个已知可运行版本恢复代码与依赖；部署清单明确排除人工维护资源的覆盖。

最后一项只是把现有部署边界写清楚，不要求本轮实现 H2 的审计、并发版本或新的备份系统。恢复旧代码也不自动等于恢复所有历史数据，应分别描述实际能力。

## 8. 补到什么程度就够了

当前值得投入的是：将 H1 的失败、回退、空结果及状态展示变成确定性回归；将 H4 的端口和依赖约束加入固定检查；明确 smoke 之外应执行的离线集成与少量页面场景。H1/H4 的新增测试由对应实施工作验证，本文不会借用原架构评估的通过数量证明本轮改动完成。

不用为了数字追求每个函数一条测试，也不必现在设一个未测量过的全仓覆盖率门槛。覆盖率可以帮助找出未执行代码，但不能证明你断言了“失败不能变成正常”这条业务承诺。

以后每增加一个重要功能，先写一句“在什么条件下，用户必须看到什么”，再判断已有哪层测试能便宜、稳定地证明它。对于个人开发，这就是可持续的验收方式。
