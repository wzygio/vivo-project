# 自动预警看板性能分析报告

日期：2026-10-20，北京时间。范围：`自动预警看板.py` 顶部全指标矩阵、`warm_alert_matrix.py` 预计算，以及 Yield 报表产出本地预警结果的方案。按用户确认方向修订：保留现有 L1 更新机制，点击图像保持现状，不再考虑跳转改造。

本报告的原始分析基于 2026-10-20 优化前源码、真实预计算日志与状态快照、只读文件检查和隔离调用计数，分析阶段未修改实现或生产数据。**随后用户授权的三项 P0 已实现于代码，交付范围见第 10 节；本文原有耗时不是优化后的实测值。** L1、计划任务与点击详情保持原机制。

## 1. 结论与优先级

1. **今天预计算的主要耗时是 Yield，而非 Q-Time。** 任务内部耗时 2,102.84 秒，约 35 分 03 秒。其中 Yield Lot 约 22 分 30 秒，占 64.19%；Yield 趋势约 6 分 47 秒，占 19.35%。两者合计 83.54%。Q-Time 整行约 1.39 秒，占 0.066%。
2. **Inline 直接读取超规记录的方向是正确的，但目前四类 OOS 没有复用已有的整本工作簿读取缓存。** 四个文件均是标准 ZIP 读取不了的企业加密格式；每个产品重新打开一次，共 28 次 COM 回退入口。隔离验证表明，复用仓库已有的整本缓存可将同范围冷读取降至 4 次；这不是已经取得的实测加速比例。
3. **Yield 应与 Inline 一样，由原报表流程产出本地预警结果，矩阵直接消费文件。** 建议分别保存 Lot 超规记录、趋势报警记录，不为矩阵另建 Yield 计算引擎或专用缓存体系。矩阵和预计算任务不再为 Yield 状态灯调用完整报表分析。
4. **直接读取本地结果不需要 Web 内存预热。** 文件是跨进程共享的结果来源；Web 内存缓存可以作为文件解析加速，但不应是结果可用的前提。真正的主要收益来自省去矩阵中的重复分析，而不只是把内存读取换成磁盘读取。
5. **保留 L1 正常更新与现有详情图像。** 输入更新后重新核对并读取本地结果是正常行为，不应将 L1 更新或缓存失效本身视为待修复问题。点击跳转不进入本轮优化范围。

首要方案是“原报表计算并发布结果 → 矩阵/预计算读取结果文件”，同时复用 Inline 已有的整本工作簿读取能力。63 格签名采集约 4.44 秒及配置重复解析属于后续读取路径优化。Yield 原报表自身的慢步骤和失败仍值得诊断，但不再把完成这项诊断作为矩阵提速的前置条件。

### 3.2 当前慢链路应由原报表拥有，矩阵退出重复分析

实际链路可见于 [矩阵装配](../../../../../app/sections/inline_domain/monitor/alert_matrix_cache.py)、[Yield 服务](../../../../../src/yield_domain/application/yield_service.py)：

```text
Yield Lot 单元格
  → get_data_health → get_raw_panel_details
  → get_lot_defect_rates
      → get_modified_panel_details
      → _get_array_times
      → get_code_level_trend_data / modifier context
      → warning lines / rate overrides
      → calculate_lot_defect_rates
  → compute_lot_oos_records → 截取上一完整 ISO 周
```

这里只为了得到一个状态灯，但冷缓存会进入完整 Lot 分析。当前默认分析窗口从“三个月前所在月的 1 日”开始，按今天为 2026-07-01 至 2026-10-20；上一完整周过滤发生在预警记录生成之后。

这说明矩阵当前承担了应由 Yield 原报表完成的结果生产。修订后的首要方案见第 3.3 节。以下保留为原报表性能调查线索，不据此新增矩阵专用的源快照或缓存机制：

- `_get_array_times` 的进程内缓存 miss 后，通过 [Yield 数据适配器](../../../../../src/yield_domain/infrastructure/report_data_adapter.py) 使用 `use_snapshot=False` 的路径访问阵列投入时间；Panel 已有 Parquet 不等于阵列投入时间也有持久快照。
- [投入时间 SQL](../../../../../src/yield_domain/infrastructure/data_loader.py) 对 `eda.spot_eda_array_hst_v` 使用 `step_id='10000'`、`SUBSTR(sheet_id,1,9) IN (...)` 后按 Sheet 求最早时间，没有事件时间界限。它有 Lot 范围，但函数谓词可能不利于普通索引；是否确实扫描很大，需要元数据、索引信息和不执行查询的计划验证，不能由源码直接下结论。
- Lot 与趋势使用不同指标 revision 构造 `snapshot_signature`，该签名又传入基础 Panel 缓存。相同产品/时间窗的两类预警可能分别反序列化、处理基础数据。这是当前重复分析的调查线索，本次通过矩阵改读结果文件避开该路径，不要求调整 L1。
- `get_data_health` 通过完整 L1 DataFrame 获取健康属性，并非独立的轻量元数据读取。大帧缓存命中仍可能有反序列化和复制成本。

**目前不能确认六个错误就是投入时间 SQL 导致。** 定时入口使用 `NullHandler`，结果日志仅保存失败单元格，状态快照又会替换原错误消息，缺少子阶段和安全错误码。后续若优化原报表，可分别记录 health、Panel、阵列时间、Code 趋势、规格/覆盖表、Lot 计算的耗时、缓存命中、行数和脱敏错误类型。

不要直接重跑大视图查询寻找慢因：先探查底层表统计规模、索引和查询计划；需要采样时限定时间、字段、返回量和超时。

### 3.3 建议方案：Yield 原报表发布两份本地预警结果

用户所说的“直接读取配置文件”，在本报告中具体指类似 Inline 工作簿的**本地预警结果文件**。规格线、修饰表等配置仍是报表计算的输入；仅仅读取规格线并不能知道哪些 Lot 或趋势已经触发报警。

[入库不良率分析看板](../../../../../app/pages/入库不良率分析看板.py) 已经在“智能预警中心”生成两类可直接发布的结果，不需要另写判定算法：

| 本地结果 | 现有产出 | 建议保存内容 | 矩阵读取后的轻量处理 |
|---|---|---|---|
| Lot 超规记录文件 | `compute_lot_oos_records(lot_data, warning_lines, time_period=30)` | 产品、超规 Lot ID、异常 Code、规格线、不良率、不良 Panel 数、入库时间、阵列投入时间 | 按产品和上一完整 ISO 周筛选，判断是否存在超规记录 |
| 趋势报警记录文件 | `AlertService.get_dashboard_alert_records(mwd_group_data, mwd_code_data)` | 产品、`period_scope`、Group/Code 层级、缺陷标识、比较周期、当前/前期不良率、命中规则 | 选择该产品当前已发布的月度/周度报警结果，判断是否非空 |

Lot 扫描当前以数据中的最大入库日为锚点回看 30 天；矩阵再按参考日的上一完整周过滤。发布时应记录扫描覆盖范围，读取端验证该范围能支持当前判定，避免有文件但周次未覆盖。趋势保持现有 period 制口径，不擅自改成只看上一周，也不把历史报警累积成永久红灯。

趋势应发布结构化记录，而不是只保存界面显示字符串。[AlertService](../../../../../src/yield_domain/application/alert_service.py) 的 `get_dashboard_alerts` 还可能包含外部基准报表比较的文本报警，当前矩阵使用的 `get_dashboard_alert_records` 不包含这一部分。为保持现有矩阵范围，建议默认保存后者；若以后希望纳入外部基准报警，应另行定义范围。

建议仍采用两份工作簿、每产品一个结果 sheet，并各带一份产品级元数据 sheet，沿用 Inline 的文件读取与原子替换思路。文件名和配置键在实施时确定，不在本轮创建资源文件。路径应注册在 `config/global.yaml → resources.yield_domain.files`，通过现有配置入口解析，分别归入 Lot 与 MWD 趋势的资源职责。

```text
既有 L1 正常更新
  → Yield 报表 application 按原规则完成分析
  → 分别发布 Lot 超规结果、趋势报警结果
      → 自动预警矩阵：读取文件、按产品/周期筛选、归约状态
      → warm_alert_matrix.py：读取同一文件、组合并保存矩阵状态
```

这是一套与 Inline 一致的报表结果发布/读取方式。`daily.json` 可以继续作为现有矩阵状态汇总产物；读取 Yield 两类结果不应要求它事先存在，也不应要求 Web application 计算缓存事先命中。

发布和读取需要满足以下约束：

1. **由原报表 application 统一发布，基础设施负责文件 I/O。** 页面调用同一用例，不能让页面和矩阵各写一套判定。发布复用报表已有的修饰、规格及趋势结果；要核对当前主报表与矩阵 `read_only`/资源版本差异，以发布的报表结果统一来源，而不是只替换接口后假定数值必然相同。
2. **只按成功生成的产品/预警类型替换其结果，保留其他产品。** 同一产品的本期有效结果应替换旧结果；如需保留历史，应明确分区或历史 sheet，不能把过去的报警直接混入本期判断。结果与对应元数据在同一次原子提交中更新。
3. **成功无报警与未计算/失败必须可区分。** 零记录也发布合法空表及元数据。至少记录产品、参考日/周期、计算覆盖、生成时间、来源新鲜度、记录数和规则/输入版本。失败保留上次成功结果，并提供本次失败或过期信息，不能将失败写成“零报警”。这些信息不等同于额外建立一套源快照机制。
4. **矩阵仅消费文件。** 文件缺失、产品未生成、范围未覆盖或版本过期时返回相应不可用状态；不隐式回退调用 `get_lot_defect_rates`、MWD 计算或数据库。否则最慢路径仍会在冷态重现。
5. **覆盖全产品发布的责任放在原报表流程。** 当前页面一次处理一个产品；只访问 M678 不会自动生成其他六个产品的文件内容。首次补齐及后续更新需纳入既有报表生成/刷新流程，必要时批量调用同一 application 生产用例，不能让矩阵承担补算职责，也不新增独立预警规则。
6. **发布不依赖图像是否展开或无关模块是否成功。** 当前页面会先加载 Sheet、Mapping，并对多个数据集统一校验后才进入预警中心。实施时应让 Lot/趋势结果在各自必要输入成功后即可发布；无关图像数据失败不应阻止已完成预警结果落盘。
7. **避免普通 rerun 反复重写文件。** 用已有输入/规则版本和结果内容判断是否需要发布；在分析结果命中内存缓存但文件尚缺时仍能完成发布。不要仅把写文件埋在某个缓存 miss 分支内，造成缓存有数据、磁盘却没有结果。

该方案把重分析保留在原报表生成环节，节省的是矩阵/预计算重复承担分析的成本，**不意味着原报表计算本身自动变快**。今天 Yield 两行约 29 分 17 秒的等待不再是矩阵读灯的必经路径；实际文件读取耗时、最终净节省和生产覆盖仍需实现后验证，不能直接承诺节省全部 83.54%。

## 4. Q-Time：范围与快照

### 4.1 是否只针对“重点站点QTime监控”

**是站点/Lot Q-Time 监控，不包括蒸镀腔室驻留时间模块。**

[Q-Time 页面](../../../../../app/pages/Q_Time监控报表.py) 分别调用站点 `render_qtime_dashboard` 与腔室 `render_chamber_dashboard`；矩阵仅装配 `build_qtime_service`，没有调用 chamber service。

但“只针对重点站点”不能解释为“只读取用户在 Q-Time 页面选中的路径”：

- [厂别公共缓存入口](../../../../../src/indicator_domain/application/qtime/cached_monitoring.py) 从 `get_filter_options(shop)` 获取该厂别全部可用路径，使用全路径、全产品 `products=()` 调用缓存。
- 矩阵依次读取 ARRAY、OLED、TP；同一矩阵上下文只合并一次，随后按产品拆分，不是为每个产品重新查三个厂别。
- Q-Time 页面产品、路径筛选主要在共享结果上做内存过滤，不改变矩阵的范围。
- application 的站点结果覆盖上月 1 日至参考日；矩阵随后将预警限定为上一完整 ISO 周。今天对应显示周为 2026-10-12 至 2026-10-19，右端不含。

因此准确表述是：**矩阵使用“重点站点QTime监控”的同一站点业务管路，覆盖三个厂别的全部可用路径，并不跟随另一个页面当前的筛选。**

这里是**源时间**，不能与显示时间直接比较。也不能由文件大小推断全库规模。

### 4.3 增加快照能优化多少

新增另一份相同源快照没有明显价值。就今天约 1.39 秒的 Q-Time 行而言，即使完全消除该行等待，对 35 分钟预热也只影响约 0.066%。

现有 Q-Time L1 继续正常更新，本次不以改造它作为性能方案。以下仅保留为可单独核查的可用性或结果签名问题：

1. 核实 TP 长期为空且过期的原因，以及源快照刷新任务是否实际部署。`get_cached_shop_monitoring` 在进入 L2 前先解析路径；空源快照可能回退查询路径，若最终无路径会触发输入校验。
2. 注意整个 Q-Time 的健康聚合：任一厂别未知/陈旧会影响合并结果，矩阵在判定产品预警之前先要求合并数据为 `fresh`。今天七格全为 `no_data`；TP 的旧空快照与这条代码路径一致，但没有运行期分支日志，尚不能确认它是唯一原因。
3. 避免首次刷新产生“旧签名 + 新结果”：当前先生成单元格签名，后执行 evaluator；若 evaluator 刷新源 Parquet，保存的首格签名会落后。今天只有 Q-Time 首个产品 M626 签名不匹配、后六格匹配，与此机制一致。应在来源版本稳定后发布结果和最终签名，并验证版本未在计算期间改变。

若未来仍需持久化派生 Q-Time 告警结果，应把它设计成可失效的结果缓存，包含源快照、决策、规则、日期和健康版本，而不是将决策后数据写回源 L1。[ADR-0023](../../../../ADR/0023-qtime-local-source-snapshot-and-decoration-boundary.md) 已明确源事实与修饰结果的边界；当前没有为性能另建一套 Q-Time 数据管路的必要。

### Inline 的优化空间在读取方式

[矩阵默认上下文](../../../../../app/sections/inline_domain/monitor/alert_matrix_cache.py) 没有注入 `oos_product_loader`，因此四类 OOS 走 [直接单 sheet 读取](../../../../../src/inline_domain/infrastructure/shared/sheet_oos_decoration_repository.py)。该函数没有整本解析缓存，每次先尝试 openpyxl，失败再进入 `_read_encrypted_xlsx_via_com`；后者每次 `DispatchEx`、打开工作簿、读 sheet、关闭并退出。

离线检查四个实际文件均 `is_standard_zip=False`，前缀为 `0000000004070702`。隔离实验在这些实际文件上保留标准读取尝试，仅替换 Office 入口，得到：

| 方式 | 4 文件 × 7 产品的冷回退次数 | 实验含义 |
|---|---:|---|
| 当前矩阵 OOS 路径 | **28** | 每个产品一次，同一文件重复 7 次 |
| 已有 `ExcelAlarmReader + ExcelAlarmStore` 路径 | **4** | 按路径、mtime、大小缓存整本工作簿，再按产品取帧 |

可优先把矩阵接到已有读取边界，而不是新增原始量测分析或另存一份无人维护的 Excel。迁移时必须核对业务列、日期排除、参数分类、flag、缺 sheet 与失败状态，不能仅比较预警条数。

28 → 4 表示高成本打开次数减少约 86%，**不等于整个矩阵加速 86%**；整本读取的数据量、Office 启动、配置和系统负载仍需实际计时。CPK / CPM 已使用整本解析缓存，其今天的低耗时也表明该方向值得优先验证。

## 6. 保留 L1 正常更新，明确结果文件与内存的职责

### 6.1 今天快照的实际可复用情况

以下为此前 10:18 左右的只读审计事实，不作为修改 L1 正常更新机制的理由：

| 行 | 匹配 / 共 7 格 | 当前行为 |
|---|---:|---|
| AOI_RS、AOI_TT、CTQ | 各 7/7 | 状态可从快照复用 |
| Yield Lot、Yield 趋势 | 各 7/7 | 当前不会仅因页面打开而必然重跑今日最慢链路 |
| SPC OOS、CPK、CPM | 各 **0/7** | 共 21 格需进入进程缓存；该进程首次 miss 时重新读取/判定 |
| Q-Time | 6/7 | M626 首格不匹配 |

今天的矩阵状态快照 09:37 发布，SPC OOS 与能力文件在 09:45 左右更新。输入更新后重新读取结果是正常行为，现有 L1 更新与签名校验继续保留。优化重点是：即使状态汇总需要重新构建，也应直接读取已经生成的业务结果文件，而不是再次进入完整报表分析。

独立隔离的 `get_cached_alert_matrix` 探针也得到相同的 22 个待重新求值格，其他格直接复用。真实运行时，这些格还可能命中 Web 进程内已更新的 L2；所以“签名不匹配”也不等于每次交互都重新打开 Excel。

### 6.2 为什么可以直接读文件，不依赖 Web 内存

**可以直接读取；Web 内存不是读取预警结果的必要条件。** 当前 Yield 状态链路之所以依赖 application 分析缓存，是因为尚未发现与 Inline 同用途的、供矩阵读取的两类已发布结果文件，矩阵目前直接调用完整分析服务。按第 3.3 节落盘后，这个依赖可以解除。

| 数据形态 | 保存什么 | 读取后是否仍需完整分析 | 修订方案中的职责 |
|---|---|---|---|
| L1 源快照 | Panel 等源事实 | 若要得到报警，仍需相应规则计算 | 继续由原报表正常更新和消费 |
| 本地预警结果文件 | 已判定的 Lot 超规与趋势报警记录 | 不需要，只做产品/周期筛选及状态归约 | 矩阵与定时任务共享的业务结果来源 |
| Web 内存缓存 | 报表 payload，或已经解析的文件内容 | 命中可减少对应计算/解析 | 可选加速；不能成为状态可用的前提 |
| `daily.json` | 已归约的矩阵单元格状态 | 匹配时可直接展示 | 保留既有状态汇总和跨进程复用 |

`warm_alert_matrix.py` 的进程内缓存不能自动搬入 Web 进程，这一点是实现事实，但**不需要通过共享 Web 内存解决本次问题**。原报表写到本地的结果，两个进程均可直接读取；即使清空 Web 内存，矩阵也应能仅靠结果文件恢复状态。

“直接读文件更快”需要区分两种比较：

- 与 Web 冷态重新读取源数据并执行完整 Yield 分析相比，小型结果文件直读能避开主要重分析链路，这是本方案的核心收益。
- 与已经命中的小型内存结果相比，磁盘解析未必更快；企业加密 Excel 还可能经过 COM。保留按文件版本缓存整本解析结果有价值，但这是读文件的附加优化，不代表矩阵必须先预热完整报表。

因此不必在“文件”和“内存”之间二选一：**结果以文件发布并跨进程共享，内存只缓存读取结果。** 矩阵缓存 miss 时读取文件，不能因此回退做完整分析。配置路径与文件版本检查也应保持轻量。

现有脚本使用 `reuse_snapshot=False`，表示本次不复用既有矩阵状态汇总。待 Yield 改为结果文件输入后，同一个设置只会促使它重新读取/归约结果，不再必然触发 Yield 重分析。无需为此修改源 L1 的更新机制。

### 6.3 热路径本身仍有重复工作

- 63 格签名采集的未剖析累计约 **4.44 秒**，不含真实预警求值。
- 独立 cProfile 探针（拦截全部 miss）总耗时 **15.33 秒**，其中 `yaml.safe_load` 被调用 **345 次**，累计 **14.81 秒**；`ConfigLoader.load_config` 14 次，`_load_yaml` 226 次。累计耗时彼此有包含关系，不能相加；剖析开销明显，15.33 秒也不能直接作为普通页面耗时。
- 同一份全局/域 YAML、资源路径和策略被多格反复解析，重复出现在缓存命中之前。应优先在一次矩阵构建中共享解析结果和同源签名；若做跨请求缓存，必须跟踪配置文件版本并返回独立对象，保留配置热更新。
- 页面在进入 `render_alert_matrix_board` **之前**调用 `get_cached_step_description_map(DatabaseManager())`。该函数冷缓存会访问工序字典；状态矩阵显示并不需要站点描述。此数据库等待未被 `warm_alert_matrix.py` 的行耗时覆盖，本轮也未联网计时，可作为后续读取路径优化，延后到实际需要站点描述的现有详情中。

### 6.4 筛选条目前只缩小显示范围

`render_alert_matrix_board` 调用的是不带筛选范围的 `get_cached_alert_matrix()`，之后才按产品、类型、厂别切片。即使用户只选 SPC / 一个产品，冷态仍可能等待全指标 × 全产品。

未来可以让交互查询只请求所选行和产品，同时保留定时任务的全范围构建。厂别目前是预警记录上的切片，不宜直接变成一套独立全量计算缓存；应继续复用相同产品结果。

## 8. 优化顺序与验收建议

| 优先级 | 建议 | 预期作用 | 验收重点 |
|---|---|---|---|
| P0：结果生产 | 原 Yield 报表 application 分别发布 Lot 超规、趋势报警两份结果文件 | 复用已有判定结果，与 Inline 结果发布方式一致 | 产品、周期、规格/修饰口径一致；成功零报警也有明确元数据；单产品更新不覆盖其他产品 |
| P0：矩阵消费 | Yield 两行改读上述文件，矩阵及预计算禁止缺文件时回退重分析 | 让最慢的 Yield 分析退出状态灯路径 | Web 内存为空时仍仅文件读取；不调用 Panel、Lot、MWD、阵列时间或生产 SQL；缺失/过期有明确状态 |
| P0：文件读取 | 四类 Inline OOS 复用已有整本工作簿读取边界，Yield 文件读取采用同类方式 | 避免每产品重复启动/打开 Office | 冷态每版本每工作簿至多读一次；热态不读；修改输入后失效 |
| P1 | 单次矩阵构建共享配置与同源签名 | 降低全部命中时仍重复解析配置的成本 | 配置解析次数、63 格热路径耗时、配置修改即时失效 |
| P1 | 结果与元数据原子发布，读取时核对版本；沿用原报表刷新流程补齐全产品 | 新结果发布后可以直接读取，旧/缺失结果不会诱发矩阵重计算 | 正常 L1 更新不变；来源变化后由生产者更新结果；文件变更触发轻量重读 |
| P1 | 工序字典延后，交互查询尊重所选指标/产品 | 状态灯不为无关查询和数据范围等待 | 不连接字典库也能展示已有矩阵状态；未选指标不求值 |
| 后续：原报表 | 对 Yield 原报表自身的慢阶段与失败做诊断 | 改善结果生产速度，不作为矩阵文件直读的前置条件 | 在原流程中记录阶段耗时与安全错误码，不新增矩阵专用计算机制 |
| 独立核查 | Q-Time TP 旧空数据与厂别健康聚合 | 与本次主要性能方案分开确认可用性问题 | 保持现有 L1；空数据与刷新失败可区分 |

本方案不要求新增并发调度、改造 L1，或让定时任务与 Web 共享内存。先完成结果发布与文件读取，再评估是否还有足够大的残余等待值得进一步改造。

也不建议简单扩大 TTL、无条件信任当天 JSON，或把未知/异常显示成正常来获得“快”：这会改变预警可信度。若增加可降级显示，应明确数据时间和可用性，并继续遵守现有源快照及维护表保留规则。

建议未来分别记录：①原报表计算与结果发布；②定时任务在全新进程中读取文件构建状态；③Web 内存为空时读取文件；④文件变化后的局部重读。点击详情保持现状，计时另列，不将其混入预计算收益。目标值应在上述基线上另行确认，本报告不承诺尚未实测的优化后秒数。
