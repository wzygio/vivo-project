# 异常片明细 API：基础知识与技术原理

编写日期：2026-10-27。面向第一次接触 API 的项目负责人。

本文是入门说明；接口名称、字段和部署方式属于建议，尚未开发上线。具体项目方案见 [异常片明细 API 开发方案](sheet-anomaly-api-development-plan.md)。

## 1. 你要开发的东西是什么

API 可以理解为一个供其他程序使用的“数据窗口”。别人按约定提交查询条件，你的系统校验身份和条件，读取允许提供的数据，再用固定格式返回。

现在的人工作业可能是“打开自动预警看板 → 选择产品 → 查看异常 → 导出”。有了 API，别人的程序可以直接发送“请给我某产品上一完整周的异常片明细”，用于自己的看板、报表或后续分析。

```text
供人使用：浏览器 → Streamlit 看板 → 表格、图像
供程序使用：对方程序 → API → JSON 明细
                         ↓
                  共同的结果读取与业务规则
```

API 不要求对方访问你的数据库，也不要求对方安装本项目。对方需要网络可达的接口地址、访问凭证，以及一份接口说明。

## 2. 一次查询如何完成

HTTP 是客户端发送请求、服务器返回响应的通信协议。这里的客户端可以是 Python 脚本或其他系统。请求包含方法、地址、请求头等，响应包含状态码和数据。[HTTP 工作原理](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)

下面是**拟议接口的教学示例**，域名和片号均为虚构，不是当前可调用的地址：

```http
GET /api/v1/sheet-anomalies?indicator=spc&product=PRODUCT_DEMO&limit=100 HTTP/1.1
Host: quality-api.example.com
X-API-Key: <由管理员分配的访问凭证>
Accept: application/json
```

| 部分 | 含义 | 本项目的例子 |
|---|---|---|
| HTTPS | 加密传输的 HTTP | 防止访问凭证和生产数据明文传输 |
| 域名或 IP | 访问哪台服务器 | `quality-api.example.com` |
| 路径 | 使用哪个功能 | `/api/v1/sheet-anomalies` |
| GET | 读取数据 | 不修改异常决策、不触发重新分析 |
| 查询参数 | 要查询的范围 | 指标、产品、厂别、片号 |
| 请求头 | 身份和通信要求 | `X-API-Key`、`Accept` |
| JSON | 便于程序处理的数据格式 | 字段名、数字、字符串、列表 |
| 状态码 | 本次请求是否成功 | `200` 成功、`503` 暂不可用 |

`v1` 是接口契约的版本。以后若必须改动字段含义，可以设计新版本，避免突然让对方程序失效。

JSON 示例：

```json
{
  "data": [
    {
      "indicator": "spc",
      "product": "PRODUCT_DEMO",
      "factory": "ARRAY",
      "sheet_id": "SHEET_DEMO_001",
      "parameter_name": "参数示例",
      "occurred_at": "2026-10-22T09:30:00+08:00"
    }
  ],
  "meta": {
    "status": "alert",
    "returned_count": 1,
    "has_more": false,
    "next_cursor": null
  }
}
```

字段是双方约定的业务含义，不应直接把内部 Excel 的全部列转成 JSON。完整建议见开发方案。

## 3. API 与现有看板有什么关系

可以复用看板背后的结果读取与筛选规则。页面文件负责界面，不能把整个页面当作 API 执行入口。

本项目已将预警生产和展示分开：原报表负责分析、识别异常并发布 Excel；自动预警看板读取已经发布的结果。共同入口是 `read_alert_result()`，详见 [看板架构](../../../../../references/domain/inline_domain/monitor/architecture-alert-dashboard.md) 和 [共同展示设计](../../../../../references/design/inline_domain/shared/architecture-published-alert-display.md)。

所以，“别人调用 API”可以只做读取，而不重新计算异常、不查询原始量测数据库。没有结果时应说明暂不可用，由原生产流程更新结果。

还要区分三个时间：

| 时间 | 含义 |
|---|---|
| 异常发生时间 | 哪天出现异常，决定属于哪一周 |
| 结果发布时间 | 原报表何时生成这份结果；现有部分文件可能没有可靠记录 |
| API 响应时间 | 对方何时来取数据 |

刚收到响应，不代表刚完成源数据更新。API 读取速度快，也不代表数据实时。首版建议沿用看板的上一完整 ISO 周，即“上周一零点至本周一零点，不包含本周一”。

## 4. 开发时有哪些组成部分

| 组成部分 | 负责什么 | 建议 |
|---|---|---|
| Web 框架 | 接收请求、检查参数、返回结果 | FastAPI |
| HTTP 服务程序 | 监听端口，把请求交给框架 | Uvicorn |
| 业务读取服务 | 读取发布结果、执行现有筛选规则 | 从现有共享逻辑提取并复用 |
| 数据模型 | 明确字段、类型、必填与可空项 | 使用明确的输入和输出模型 |
| 访问控制 | 识别调用方，限制能读取的范围 | 独立凭证和产品／厂别授权 |
| 部署与运维 | 让程序持续运行，记录失败并恢复 | 内网主机、日志、进程托管 |

FastAPI 支持基于 Python 类型声明的数据校验，并可生成 OpenAPI 接口描述及交互文档。这可以减少手写接口说明与代码不一致的问题，但不会自动替你确定业务规则或完成权限管理。[FastAPI 官方功能说明](https://fastapi.tiangolo.com/features/)

本项目目前是 Streamlit 应用，`pyproject.toml` 没有声明 FastAPI、Uvicorn。采用它们属于后续开发建议，不是已经具备的服务能力。

## 5. 必须知道的几个原则

### 5.1 鉴权与授权是两回事

鉴权回答“你是谁”；授权回答“你可以看哪些产品和厂别”。例如，某系统的凭证有效，但只能查询 ARRAY 厂别，仍不能读取 OLED 数据。

首版可以为每个调用系统分配独立 API Key，通过请求头提交。服务端保存校验材料及授权范围，支持停用和轮换。不要把密钥放在 URL、文档示例或日志里。浏览器前端也不能安全保存长期共享密钥；如果调用方是网页，应另行设计登录或后端转发。

现有页面的显示模式开关不能充当 API 身份认证。API 对外只能返回获准的公开业务字段和状态。

### 5.2 成功零条与读取失败不同

| 情况 | 对方应如何理解 |
|---|---|
| `200`，有效结果中没有命中记录 | 查询成功，当前范围没有可提供的异常明细 |
| `401` | 没有有效凭证，需要检查身份 |
| `403` | 凭证有效，但无权访问请求范围 |
| `422` | 参数不符合约定，需要修正请求 |
| `429` | 请求过于频繁，应等待后重试 |
| `503` | 当前结果暂不可用，应稍后重试 |

不能把缺文件或读取失败一律返回成 `200` 加空列表，否则对方会误认为“没有异常”。对外错误信息用业务语言，技术原因留在服务端日志，通过请求编号排查。

### 5.3 分页和限流保护服务

分页是“一次取一部分”。例如每次最多 500 条，返回下一页游标，对方继续读取。限流是“限制单位时间请求次数”。二者解决的问题不同，通常都需要。

固定查询范围、超时、并发上限也很重要。OWASP 将缺少执行时间、每页记录数等限制列为 API 资源消耗风险。[OWASP API 资源消耗说明](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)

本项目读取 Excel 时，分页通常是在解析和筛选之后进行；返回 100 条不等于只读取 Excel 的 100 行。实际文件大小和首读耗时需要另行验证。

### 5.4 缓存提高速度，但不能代替生产更新

缓存保存近期读取结果，避免重复解析同一本工作簿。文件、筛选政策或公开展示政策变化后，缓存应相应失效。

API 和 Streamlit 即使运行在同一台电脑，也可能是不同进程，不能默认共享内存缓存。它们可以共享发布文件，各自管理内存。多进程通常有各自的内存和资源开销。[FastAPI 部署概念](https://fastapi.tiangolo.com/deployment/concepts/)

### 5.5 “单片”与“明细条数”需要约定

一片可能在多个站点、多个指标上报警，所以三条明细不一定代表三片异常片。

现有看板还有名称与粒度的差异：Yield 的“单片异常”实际是 Lot 超规，Q-Time 明细也包含 Lot，AOI_RS 同时包含 By Lot 和 By Sheet。开发前要明确是“严格逐片”，还是“看板中名称为单片异常的分组”。不能根据 Lot 报警推断其中每片都异常。

## 6. 如何让别人真正用起来

写完 Python 接口只是第一步，还需要确定服务主机、访问地址、网络权限、HTTPS、调用凭证、运行时间和维护负责人。

`127.0.0.1` 只能访问本机；让服务器监听网卡也不等于对方一定能访问，还受路由、防火墙和企业网络策略影响。首版建议在公司内网提供，经正式入口转发至 API 服务。是否允许跨网访问，应单独确定。

交付给调用方的内容应包括：测试／正式地址、凭证领取方式、接口说明、请求与响应示例、数据周期、分页方式、错误处理方法和联系人。对方一般不需要数据库账号。

你首先需要决定的业务问题只有三个：**提供哪些异常、提供给谁、允许多旧的数据**。框架、字段映射和缓存机制可以由开发人员落实。
