# Matt Skills：PRD、Issue、需求澄清与执行计划的分工

本文回答一个常见混淆：需求文档、工作项（Issue）和执行计划都可能包含“要做什么”，但它们不是同一种东西。本仓库的工作项使用 Local Markdown Issue，当前约定见 `docs/agents/issue-tracker.md` 与 `docs/agents/triage-labels.md`。

## 先给结论

1. **PRD（Product Requirements Document，产品需求文档）首先是需求/规格文档，不是执行计划。**它定义问题、目标用户、预期结果、范围和验收边界。
2. **Issue 不是 Debug 专属。**一个 Issue 是可追踪、可流转、可交付的工作单元；它可以是新功能、缺陷、重构、迁移或文档任务。
3. **计划不是 PRD，也不是 Issue 的状态列表。**计划负责把一段工作按顺序、依赖、风险和进度组织起来；一个计划通常会对应多个 Issue。
4. `$to-prd`、`$to-issues`、`$create-local-markdown-issue` 是不同粒度的“需求到工作项”工具；`$grill-me` 系列用于澄清/质询决策；`$planning-with-files` 用于持久化执行计划。它们可以组合，不是互斥关系。

## 四种产物的边界

| 产物 | 核心问题 | 典型内容 | 不等同于 |
|---|---|---|---|
| 需求 / PRD | 为什么做、为谁做、做到什么程度 | 问题、方案、用户故事、范围、验收、非目标 | 执行顺序与每日进度 |
| Issue | 这个独立工作项由谁在什么状态下完成 | 当前事实、目标、验收、范围、状态、评论 | 完整产品规格或项目总计划 |
| 执行计划 | 这批工作如何推进 | 阶段、依赖、风险、验证、进度 | 需求本身或单一工作单 |
| ADR | 为什么作出一个重要且持久的技术决策 | 背景、决策、备选方案、后果 | PRD 或任务清单 |

因此，可以把它们理解为如下关系：

```text
需求 / PRD（定义正确的目标）
        ↓
执行计划（安排如何完成） ──→ 多个 Issue（可领取、可流转的工作单元）
        ↓                                      ↓
证据、测试、交付记录                    triage → ready-for-agent → 开发
```

小任务不必经过所有层：一个明确的 Bug 可以直接成为一个 Issue；而跨多个模块、多个用户故事的大功能通常先写 PRD，再拆分 Issue。

## 1. PRD 是需求文档，而不是计划文档吗？

是。PRD 的主要职责是把模糊想法变成可共同确认的需求规格：要解决什么问题、哪些用户受益、行为如何验收、哪些事情明确不做。

本机的 `$to-prd` 会生成的 PRD 还包含“Implementation Decisions（实现决策）”和“Testing Decisions（测试决策）”。这使它比纯业务需求更接近**可交付规格**，但不改变其本质：它仍然不负责记录任务执行顺序、每一步负责人、实时完成状态或调查日志。后者应由 Issue 追踪器和文件化计划承担。

一个实用判断方法：

- 想回答“用户最终会获得什么？”——写 PRD。
- 想回答“先做什么、依赖什么、现在做到哪一步？”——写计划。
- 想回答“这一块可以被谁独立领取、验收和关闭？”——创建 Issue。

## 2. `$to-prd` 与 `$to-issues` 有什么区别？不是“开发 vs. Debug”

| Skill | 输入 | 主要输出 | 最适合的时机 |
|---|---|---|---|
| `$to-prd` | 当前对话、代码库和领域上下文 | 一份 PRD | 需求范围较大，需要先对目标、用户故事和边界达成共识 |
| `$to-issues` | 已有的计划、规格或 PRD | 多个彼此可交付的垂直切片 Issue | 已知道要做什么，需要把工作分派/并行化/追踪 |

`$to-prd` 会综合上下文写出一份完整需求规格；它不是把一句需求直接拆成任务清单。`$to-issues` 则假定已有足够稳定的来源材料，并将其拆为“薄而完整”的端到端切片，例如“从数据读取到界面展示再到测试”的一个小功能，而不是把“建数据库 / 写接口 / 写按钮”拆成彼此难以独立验收的横向工序。

两者与工作类型无关：

- 新功能可以先有 PRD，再拆出多个 enhancement Issue。
- 缺陷可以直接创建一个 bug Issue，然后 triage、诊断和修复。
- 重构、迁移和技术债也都可以使用 Issue；是否需要 PRD，取决于是否需要先定义较大的目标和范围。

## 3. `$to-issues` 能取代 `$create-local-markdown-issue` 吗？

**部分场景可以，但不能把它们视为完全替代。**

`$create-local-markdown-issue` 的定位是“原始请求的单卡入口”。面对一条功能需求、Bug 描述、开发提示词或对话内容时，它会先结合代码和文档调查，再形成一个有当前事实、目标、可执行验收条件、范围、待澄清问题和初始 triage 状态的 Local Markdown Issue。它适合“我有一个具体请求，先把它变成一张可审查卡片”。

`$to-issues` 的定位是“已有方案的多卡拆分器”。它更适合“我已经有 PRD、规格或计划，现在要拆成多张可独立交付的卡”。它还会与使用者确认切片和依赖关系。

建议按下面选择：

| 情况 | 优先使用 | 原因 |
|---|---|---|
| 一条明确但尚未调查的需求或 Bug | `$create-local-markdown-issue` | 先把事实、范围、验收和疑问补齐成一张卡 |
| 一份已确认的 PRD 要交给多个 Agent/开发者 | `$to-issues` | 需要拆成多张可独立领取的垂直切片 |
| 只有一个小且范围稳定的功能 | `$create-local-markdown-issue` | 不需要为了拆分而制造多张卡 |
| 业务目标大、尚未确定范围 | `$to-prd`，必要时再 `$to-issues` | 先定义“做对什么”，再决定“拆成什么” |

这并不要求手工自建 Markdown 卡：调用 `$create-local-markdown-issue` 本身就是自动创建本仓库 Local Markdown Issue 的方式。当前 Harness 约定的根目录是 `.scratch/`：功能 PRD 可位于 `.scratch/<feature>/PRD.md`，实现卡位于 `.scratch/<feature>/issues/<NN>-<slug>.md`。卡片随后通过 `needs-triage`、`needs-info`、`ready-for-agent` 等规范状态流转。

## 4. `$grill-me` 和 `$grill-with-docs` 都是在“压力测试需求”吗？

可以把它们理解为**需求、方案或计划的决策质询器**，但“只用于需求文档”不够准确。

| Skill | 主要行为 | 适合何时使用 | 是否负责写执行计划 |
|---|---|---|---|
| `$grill-me` | 一次问一个关键问题；若答案可从代码获得，会先查代码 | 方案、设计或计划存在关键选择、风险或歧义 | 否 |
| `$grill-with-docs` | 在上述质询外，校验领域术语与项目文档；术语澄清后可更新 `CONTEXT.md`，必要时建议 ADR | 决策会影响领域语言、既有设计或长期架构约定 | 否 |

两者的目标是让决定经得起追问，例如“CPK 预警到底只看日 CPK 还是同时看月/周？”、“参数名称是否有独立编码字段？”、“这个缓存决策是否会影响既有 ADR？”。它们可以在写 PRD 前、Issue triage 时、设计评审时或计划开始前使用。

它们产生的是**已澄清的决策和边界**，不是阶段表。若质询发现的结论需要长期保留，`$grill-with-docs` 可以帮助同步领域文档，并对难以回滚或有明显取舍的决定建议 ADR；之后仍应使用计划工具安排落实步骤。

## 5. Matt Skills 没有“编写执行计划”的文档吗？可以用 `$planning-with-files` 补充吗？

就这次涉及的 Matt Skills 而言，可以这样理解：

- `$to-prd` 负责需求规格；
- `$to-issues` 负责把已有方案拆成工作项；
- `triage` 负责工作项状态判断；
- `tdd`、`diagnose` 等负责实施/排障方法；
- 它们没有取代一个持续维护“阶段、依赖、发现、进度”的执行计划文件。

**可以，而且推荐在复杂工作中用 `$planning-with-files` 补充。**它在仓库 `.planning/<plan-id>/` 下维护三类文件：

| 文件 | 内容 |
|---|---|
| `task_plan.md` | 阶段、状态、守则、依赖和验证节点 |
| `findings.md` | 调研证据、代码发现、已确认的约束 |
| `progress.md` | 实际执行日志、测试结果和错误记录 |

它和 Issue 追踪器的分工是：**计划管理一段工作如何推进；Issue 管理一个可交付工作单元的生命周期。**例如，一个“CPK 告警中心”计划可以包含调查、卡片 triage、测试、实现、回归和 ADR 阶段；其中只有“实现 CPK 告警中心”这项工作也许是一张 Issue，或者在更大需求中被拆成多张 Issue。

## 本仓库推荐组合流程

### 场景 A：单一功能或单一 Bug

```text
原始需求/报错
  → create-local-markdown-issue
  → triage
  → ready-for-agent
  → tdd（Bug 复杂时可先 diagnose）
  → 测试与交付记录
```

如果涉及多个模块、外部依赖或超过几步验证，再并行维护 `$planning-with-files` 的执行计划即可；不必先写 PRD。

### 场景 B：较大产品能力或多个用户故事

```text
原始构想
  → grill-me / grill-with-docs（仅在关键决定不清楚时）
  → to-prd
  → 人工确认需求边界
  → planning-with-files（安排阶段、风险和验证）
  → to-issues（拆成可独立交付的纵向切片）
  → triage → tdd / diagnose → 验证
```

这里的顺序不是机械规定：若 PRD 已经足够清楚，可跳过质询；若只有一个独立小任务，可跳过 PRD 和多卡拆分。

### 场景 C：术语或架构决策会影响长期维护

```text
需求/设计草案
  → grill-with-docs
  → 更新领域术语或记录 ADR（仅当决策难以回滚或存在重要取舍）
  → PRD、计划或 Issue 中引用该决定
```

## 最后的一句选择口诀

**想清楚目标，用 PRD；想把一件事流转，用 Issue；想把一批事推进，用计划；想发现没想清楚的决定，用 Grill。**
