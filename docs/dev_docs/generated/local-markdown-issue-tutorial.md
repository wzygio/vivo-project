# 如何创建与维护 Local Markdown Issue

本项目已经选择 Local Markdown 作为 Issue tracker。换句话说，一条 Issue 不是 GitHub 网站上的卡片，而是仓库内一份可追溯的 Markdown 文件。

本教程以当前项目配置为准：

- 工作项和 PRD：`.scratch/`
- 状态名称：见 `docs/agents/triage-labels.md`
- 领域上下文：根 `CONTEXT.md`，以及制造术语 `references/design_references/domain/GLOSSARY.md`

可直接复制的模板位于同目录：[local-markdown-issue-template.md](local-markdown-issue-template.md)。

## 先记住目录规则

一个功能/主题使用一个目录；该主题下可以有一份 PRD 和多条实施 Issue：

```text
.scratch/
└── indicator-improvement/
    ├── PRD.md
    └── issues/
        ├── 01-parse-spec-versions.md
        └── 02-render-tightening-report.md
```

目录与文件命名规则：

- `<feature-slug>`：小写英文、数字和连字符，例如 `indicator-improvement`；
- Issue 编号：从 `01` 开始，按创建顺序递增；
- `<slug>`：短而具体，例如 `parse-spec-versions`；
- 原始需求仍保留在 `docs/dev_prompt/`，Issue 用 `Source:` 链接它，而不是复制整份材料。

`.scratch/` 目前不存在是正常的。首次创建 Issue 时再新建目录即可。

## 一条 Issue 应该写什么

最小可用 Issue 至少包含：

1. 标题：说明具体要处理什么；
2. `Category`：`bug` 或 `enhancement`；
3. `Status`：当前 triage 状态；
4. `Source`：原始需求或报告的路径；
5. 当前现象/背景与期望结果；
6. 可验证的验收条件；
7. 明确不做什么；
8. 评论和调查记录。

模板中的字段不是为了填表而填表。它们分别让未来的你或 Agent 回答：

```text
这是哪一类工作？        → Category
现在能不能做？          → Status
为什么要做、原始材料在哪？→ Source / Context
完成后应看到什么？      → Acceptance criteria
什么不要顺手扩大？      → Out of scope
已经查过什么、问过什么？ → Comments
```

## 从零创建第一条 Issue

以“比较指标规格版本”为例：

### 1. 建立功能目录与 Issue 文件

在项目根目录创建：

```text
.scratch/indicator-improvement/issues/01-parse-spec-versions.md
```

将模板复制进去，填写标题、类别、状态和来源。

初次创建时，通常使用：

```markdown
Category: enhancement
Status: needs-triage
Source: docs/dev_prompt/feat-Indicator_Improvement.md
```

`needs-triage` 的意思是“这条工作已被记录，但范围、信息或执行方式尚未确认”。它不是失败，也不代表 Agent 已经开始编码。

### 2. 写清“当前事实”和“期望结果”

不要只写“实现指标分析”。应写成可判断的行为：

```markdown
## Current context

规格文件位于 resources/project_files/。同一产品存在多个版本；
监控规格字段可能是数值，也可能是复杂文本。

## Desired outcome

能够比较同一产品的相邻版本，列出被收严的规格名称与数量。
无法稳定解析的表述按已确认的业务规则处理。
```

如果你还不知道“收严”的具体判断规则，不要假装已明确；把问题写在 `## Questions to resolve`，保留 `needs-triage` 或改为 `needs-info`。

### 3. 写验收条件，而不是实现步骤

验收条件应描述外部可见结果：

```markdown
## Acceptance criteria

- [ ] 能读取指定产品的多个规格版本。
- [ ] 输出每一相邻版本之间的收严规格数量和具体名称。
- [ ] 无法解析的规格按已确认规则处理，并在结果中可识别。
- [ ] 输出结果可由测试或示例数据复核。
```

以下写法过于含糊：

```markdown
- [ ] 把代码写好。
- [ ] 修复 bug。
```

### 4. 写出不在本次范围内的内容

范围边界能防止工作在实施中失控：

```markdown
## Out of scope

- 不修改原始规格 Excel 文件。
- 不在本条 Issue 中实现所有客户汇报页面。
- 不为无法解析的历史文本发明新的比较规则。
```

## 五种 Status 怎么用

| Status | 何时使用 | 下一步 |
| --- | --- | --- |
| `needs-triage` | 新建但尚未充分评估 | 阅读需求、代码与领域文档 |
| `needs-info` | 缺少必要事实 | 在评论中提出具体问题，等待回答 |
| `ready-for-agent` | 范围、边界、验收条件足够完整 | 可交给 Agent 独立实现 |
| `ready-for-human` | 需要业务拍板、权限、线下操作或人工审美 | 交给相应人员处理 |
| `wontfix` | 有稳定理由决定不处理 | 记录理由，保留文件供追溯 |

`Category` 与 `Status` 不要混淆：

```text
Category: bug                # 这是什么类型的工作
Status: needs-info           # 这条工作现在处于什么阶段
```

## 如何追加评论和调查记录

所有后续记录写在 `## Comments` 下，按时间从旧到新追加。需要区分事实、推测和待确认问题。

```markdown
## Comments

### 2026-07-14 — Initial triage

> *This was generated by AI during triage.*

**Established:**

- 需求源为 `docs/dev_prompt/feat-Indicator_Improvement.md`。
- 产品推出顺序已定义为 M678 → M626 → Z571。

**Open questions:**

- “收严”是否只比较数值上限/下限，还是也比较文本条件？
- 图像的最终展示位置和验收人是谁？
```

`triage` 产生的评论必须带 AI 免责声明。你手工添加的业务记录不必伪装成 AI 生成内容。

## 何时转为 `ready-for-agent`

满足以下条件后才适合转为 `ready-for-agent`：

- `Category` 明确；
- 原始需求和相关领域词汇已找到；
- 当前行为与期望行为都写清楚；
- 验收条件可验证；
- 关键问题已解决，或明确记录为依赖；
- 不在范围内的内容已写出；
- 没有需要人类权限、业务拍板或线下操作的隐藏前提。

复杂任务可在 Issue 中加入 `## Agent Brief`，让后续 Agent 不必重新猜测需求。Brief 应描述行为与接口契约，不要依赖容易过期的行号。

## 关于“完成”与“关闭”的当前约定

当前 `docs/agents/triage-labels.md` 只定义了五个 **triage 状态**，没有定义 `completed` 或 `closed` 这类实施完成状态。

因此，不要在未经约定的情况下自行把 `Status` 改成 `completed`，否则后续 `triage` 无法理解它。实施结束时可先：

1. 在 `## Comments` 记录交付内容和验证结果；
2. 链接相关提交、PR、输出或测试；
3. 请维护者决定是否为本项目增加“完成/归档”约定。

如果以后决定增加完整关闭生命周期，应同步更新 `docs/agents/issue-tracker.md` 和 `docs/agents/triage-labels.md`，而不是只在某一张卡里临时发明新状态。

## 与 Plan、PRD 和 ADR 的关系

```text
Issue  = 一次具体工作的状态与讨论
PRD    = 较大需求的整体目标与范围
Plan   = 实现某项工作前的路线和验证步骤
ADR    = 重要、难逆架构选择及其理由
```

常见组合：

```text
一个大需求
  └── PRD.md
        ├── Issue 01：解析与比较规格版本
        │     └── Plan：复杂时再写实施计划
        └── Issue 02：输出汇总表与图像

若中途决定“所有复杂文本规格均视为不收严”且该决定难逆、需要长期解释
  └── ADR：记录该决定及替代方案
```

## 创建前检查清单

- [ ] 功能目录使用小写 kebab-case 名称。
- [ ] Issue 文件在 `issues/` 下并有两位编号。
- [ ] `Category` 是 `bug` 或 `enhancement`。
- [ ] `Status` 是已配置的五种状态之一。
- [ ] `Source` 指向原始需求或问题材料。
- [ ] 验收条件能被验证。
- [ ] 已写明不在范围内的事项。
- [ ] 评论区只记录事实、结论、问题与验证证据。
