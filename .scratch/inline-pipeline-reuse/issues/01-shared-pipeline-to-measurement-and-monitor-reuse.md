# Inline Pipeline 复用：共享逻辑下沉 measurement + monitor 复用 spc/ctq/aoi_tt 数据管线

Category: `enhancement`  
Status: `ready-for-agent`

## Current context

- ADR-0012 已将三厂测量 DAO 与原始快照集中到 `infrastructure/measurement/`，但 `infrastructure/spc/spc_repository.py` 仍承载跨模块复用逻辑：白名单 merge + `data_type` 注入（`:184-201`）、异常点过滤 `_apply_outlier_filters`（`:225-397`）、LOSS 排除参数过滤（`:179`）、主制程追溯纯函数（`infrastructure/spc/main_process_trace.py`）、规格线 YAML 覆盖（`:46-152`）。CTQ 与 monitor 均经由它派生（`infrastructure/ctq/ctq_repository.py:18`、`composition.py:42-50`）。
- spc 因此不是与 ctq/aoi_tt/monitor 平行的业务模块，而是"共享制备 + SPC 业务"的混合体。
- monitor 对全部 data_type 统一走 SPC 口径修饰 `prepare_decorated_spc_data`（`monitor_service.py:306,527`），而 CTQ 报表页走 `ctq_sheet_oos_decoration.xlsx`（`ctq_data_decoration.py:18,71-79`，一个文件、每产品一个 sheet）；同一 CTQ sheet 两处口径不一致。
- monitor 的 AOI 行来自白名单 `data_type IS NULL → AOI` 分类，且被 SPC 修饰文件意外覆盖；aoi_tt 模块按规格表 `param_type IS NULL` 识别 TT、保留 lot、不做修饰。两者同底（共享快照）但口径不同（证据见 Comments）。
- `get_scrap_data` + `_infer_factory_from_step` 仅 monitor 消费，数据源为独立 Excel（`resources/scrap_sheets.xlsx`），与 measurement 三 port 零耦合，现位于 spc_repository。
- `src/inline_domain/composition.py:18` 的 import 缺 `src.` 前缀，与其余 import 不一致。

## Desired outcome

- 段 1：所有可复用制备逻辑（清洗/去重、白名单 + data_type 注入、异常点过滤、主制程追溯、规格线覆盖机制）归属 `infrastructure/measurement/`；spc 成为与 ctq/aoi_tt/monitor 平行的薄业务模块。调用顺序保持现状（LOSS 过滤在 data_type 过滤之前、异常点过滤在其后），各报表口径不变。
- 段 2：monitor 的 CTQ 数据切换到 ctq 修饰口径（D2 已确认）；monitor 的 AOI 数据与 aoi_tt 对齐到"同源快照 + 不经 SPC 口径修饰"（D3：aoi_tt 在范围内，aoi_rs 不在）。
- 修饰 + Sheet 特征计算的重复执行被消除，spc/ctq/monitor 同源同结果（一致性目标），且不违背"各模块 repository 直接服务本模块 application"的 DDD 结构。
- 报废数据逻辑归属 monitor 自己的 infrastructure。
- `references/domain/Inline_domain/` 新增 infrastructure 架构规范技术文档；设计文档 `docs/dev_docs/generated/Inline_domain/monitor_data_reuse_evaluation_and_design.md` 更新为最终方案。

## Acceptance criteria

- [ ] `infrastructure/measurement/` 承载共享制备管线；`infrastructure/spc/` 仅保留 SPC 业务投影，不再被 ctq/monitor 依赖其中的可复用逻辑。
- [ ] 制备管线调用顺序与迁移前一致（LOSS→白名单/data_type→异常点→维度过滤→追溯），SPC/CTQ/monitor 各页面数据口径回归一致。
- [ ] monitor 看板与下钻中 data_type=CTQ 的行经 ctq 修饰文件口径处理，与 CTQ 报表页结果一致。
- [ ] monitor 中 data_type=AOI 的行不经 SPC 修饰文件处理；aoi_tt 报表行为不变。
- [ ] 同一产品同一刷新周期内，修饰 + Sheet 特征计算按 (prod, 口径) 只执行一次并被 spc/ctq/monitor 共享命中。
- [ ] `get_scrap_data` 迁入 monitor infrastructure，报废看板行为不变。
- [ ] 强刷链路完整：页面清缓存覆盖共享缓存，`snapshot_signature` 失效机制有效。
- [ ] 定向单元/集成测试与 SPC/CTQ/AOI_TT/自动预警 E2E 全部通过。
- [ ] `references/domain/Inline_domain/` 新增 infrastructure 架构文档；设计文档定稿。

## Out of scope

- 不改变 monitor 的 OOS/OOC/SOOS 判定、时间桶、合规洗白、聚合口径；不改变 aoi_tt 的 TT 公式与 lot 粒度。
- 不统一 monitor-AOI 与 aoi_tt 的参数识别集（白名单 NULL→AOI vs 规格表 param_type NULL）：属行为变更，单独立项。
- 不迁移 `spc_sheet_oos_decoration.xlsx` 中历史积累的 CTQ 行 flag 数据（代码外数据工作）。
- 不处理 aoi_rs 模块；不改数据库表结构。
- 不重构 `_apply_outlier_filters` 的加密 xlsx COM 写副作用（仅平移，单列后续优化）。

**Category:** enhancement  
**Summary:** 将 `infrastructure/spc/spc_repository.py` 中的跨模块制备逻辑下沉至 `infrastructure/measurement/`，使 spc 成为平行薄业务模块；monitor 按数据类型复用 spc/ctq/aoi_tt 同源管线（CTQ 切 ctq 修饰口径，AOI 免 SPC 修饰），消除修饰与特征计算的重复执行。

**Current behavior:**

- 白名单+data_type 注入、异常点过滤、主制程追溯、规格线 YAML 覆盖位于 spc_repository，ctq/monitor 经它派生（顺序：LOSS 过滤 → 白名单/data_type → 异常点 → 维度过滤 → 追溯）。
- monitor 对 ALL 类型统一走 SPC 修饰文件；CTQ 报表页走 ctq 修饰文件（`resources/ctq_sheet_oos_decoration.xlsx`，每产品一个 sheet），同引擎不同文件。
- monitor 的 AOI 行被 SPC 修饰文件意外覆盖；aoi_tt 无修饰。
- 修饰+特征计算在 spc/ctq/monitor 三处各自重复执行；`get_scrap_data` 位于 spc_repository 但仅 monitor 消费。
- `composition.py:18` import 缺 `src.` 前缀。

**Required behavior:**

- 共享制备管线归属 `infrastructure/measurement/`，调用顺序逐行为保持；spc/ctq/aoi_tt/monitor 为平行薄模块，各自 repository 直接服务本模块 application。
- monitor 的 CTQ 行经 ctq 修饰口径；AOI 行不经 SPC 修饰；报废逻辑迁入 monitor infrastructure。
- 修饰+Sheet 特征按 (prod, 口径) 缓存共享，spc/ctq/monitor 同源同结果；强刷链路（页面清缓存 + snapshot_signature）覆盖共享缓存。
- 产出 `references/domain/Inline_domain/` infrastructure 架构文档与定稿设计文档。

**Key interfaces:**

- `application/ports/measurement_snapshot.py` 三 Protocol（MeasurementSnapshotPort/MetadataPort/MainProcessHistoryPort）保持不变；制备管线作为 measurement 层的派生能力暴露给各模块 repository。
- 修饰引擎 `core/spc/spc_sheet_oos_decoration.py` 不变，通过 `decoration_file_name`/`decoration_sheet_name` 参数按口径路由。
- 缓存边界遵守 ADR-0001：`st.cache_data` 只跨 DataFrame/原生容器/标量。

**Edge cases:**

- 制备管线保序：LOSS→data_type→异常点（monitor ALL 时异常点规则仍作用于 AOI 行）。
- ctq 修饰文件缺某产品 sheet 时按空修饰处理（引擎既有语义）。
- 数据库失败时沿用快照降级；空数据/缺白名单时行为不变。
- AOI 行免修饰后 monitor 的 AOI 报警数可能变化（预期内，D3 对齐结果）。

**Verification expectations:**

- 定向单元/集成测试（measurement 制备、spc/ctq/monitor 服务、修饰路由）+ SPC/CTQ/AOI_TT/自动预警 E2E 全部通过；全量 pytest 不引入新失败（基线 7 个既有失败除外）。

**Out of scope:**

- monitor 判定/聚合口径、aoi_tt 公式、AOI 参数识别集统一、历史 CTQ flag 数据迁移、aoi_rs、outlier COM 写副作用优化。

## Comments

### 2026-08-13 — Initial note

> *This was generated by AI during triage.*

代码证据（explore 核查）：

- 共享逻辑位置：`spc_repository.py:166-223`（制备管线）、`:225-397`（异常点，含 COM 解密写 CSV 副作用）、`main_process_trace.py`（纯函数，仅 spc_repository 使用）、`:46-152`（规格覆盖，ctq/monitor 实际共用，键名 `spc_spec_override`）。
- 顺序陷阱：LOSS 过滤（`:179`）早于 data_type 过滤（`:193-201`），异常点过滤（`:202`）晚于它；monitor 传 "ALL" 时异常点规则作用于 AOI 行。迁移必须保序。
- CTQ 修饰现状：`resources/ctq_sheet_oos_decoration.xlsx`，根目录扁平、每产品一个 sheet（`ctq_data_decoration.py:18,30-38`）；与 SPC 共用 `core/spc/spc_sheet_oos_decoration.py` 引擎，仅文件名不同。用户"汇总到一个文件"的口径与代码一致；题目中 `resources/<prod>/ctq/` 描述已过时。
- monitor-AOI 与 aoi_tt 的差距（D3 事实核查）：①参数识别不同（白名单 `data_type NULL→AOI` vs 规格表 `param_type IS NULL`）；②monitor-AOI 当前被 SPC 修饰文件覆盖，aoi_tt 无修饰；③monitor 丢 lot_id 聚 sheet 特征，aoi_tt 保留 lot；④语义不同（报警判定 vs 平均每片 TT 个数）。同底：均为 `data/<prod>` 共享快照。结论：可对齐到"同源 + 免 SPC 修饰"，参数集统一属行为变更，列入 Out of scope。
